넥사크로(Nexacro)가
무엇인지부터 정리한다

넥사크로는 (주)투비소프트가 만든 국산 RIA(Rich Internet Application) 개발 플랫폼입니다. 공공기관, 금융권, 대기업 SI 프로젝트의 화면 개발 표준으로 널리 쓰이고 있어서, 전문가 양성 과정을 준비하며 배운 내용을 이 페이지에 순서대로 정리해두려고 합니다.

실무 SI 표준

공공/금융 SI 프로젝트에서 화면 개발 표준 툴로 채택되는 경우가 많아 취업 실무와 바로 연결됩니다.

컴포넌트 기반 개발

Grid, Div, Dataset 등 컴포넌트 단위 개발 방식을 익히면 다른 RIA/UI 프레임워크 이해에도 도움이 됩니다.

데이터셋 중심 구조

화면과 서버 통신을 Dataset이 매개하는 구조라, 데이터 바인딩 개념을 확실히 잡아둘 필요가 있습니다.

넥사크로의 특징

스크립트 + 컴포넌트 결합 구조

화면(Form)에 컴포넌트를 배치하고, 각 컴포넌트의 이벤트에 JavaScript 유사 문법의 스크립트를 붙이는 방식으로 동작을 구현합니다. Nexacro Studio의 스크립트 에디터에서 직접 로직을 작성합니다.

화면에서 서버로 데이터를 보내고, Controller·Mapper 등을 거쳐 처리한 뒤 다시 화면으로 돌려받는 전체 흐름을 도식화하면 다음과 같다.

1

화면 (클라이언트)

this.transaction()으로 서비스 URL을 호출하며 요청 Dataset을 함께 전송

2

Controller

요청을 받아 어떤 서비스 로직으로 넘길지 라우팅

3

Service / Mapper (SQL 실행)

MyBatis Mapper의 SQL을 실행해 DB를 조회·처리

4

DB

조회·처리 결과를 Service/Mapper로 반환

5

화면 (클라이언트) — 응답

처리 결과를 Dataset(PDF/XML)으로 응답받아 화면을 갱신

코드 예시

// 클라이언트: 서비스 호출
this.transaction(
  "svcMemberList=member.list",
  "ds_search=input", "ds_member=output", "",
  this.cb_search, ""
);
// 서버: 요청 Dataset을 받아 조회 결과를 응답 Dataset에 채움
public void memberList(PlatformData reqPd, PlatformData resPd) {
  DataSet dsSearch = reqPd.getDataSet("ds_search");
  DataSet dsMember = resPd.newDataSet("ds_member");
  // dsSearch 조건으로 SQL 실행 후 dsMember에 결과 매핑
}

서비스에서 Mapper를 호출한 뒤 MyBatis가 XML 속 SQL을 찾아 실행하고 결과를 매핑해 돌려주기까지의 흐름을 도식화하면 다음과 같다.

1

서비스 코드 — Mapper 호출

예: sqlSession.selectList("selectMemberList", params)

2

MyBatis — 매퍼 XML 탐색

호출한 id와 일치하는 <select> 구문을 찾음

3

파라미터 바인딩

#{ } 자리에 전달받은 값이 채워져 최종 SQL 완성

4

DB 실행

완성된 SQL이 DB에서 실행되어 결과 Row들을 반환

5

결과 매핑 — 응답

resultType(hashmap 등) 기준으로 컬럼 별칭(alias)에 맞춰 매핑되어 반환

코드 예시

<select id="selectMemberList" resultType="hashmap">
  SELECT
    member_id   AS id,
    member_name AS name,
    age
  FROM member
  WHERE dept_cd = #{deptCd}
  ORDER BY member_id
</select>

이벤트 핸들러 & 함수 문법

이벤트를 더블클릭하면 핸들러 함수가 자동 생성된다. this.함수명 = function(obj, e) {} 형태(함수 표현식)를 압도적으로 많이 쓰며, this는 그 스크립트가 속한 Form 자신을 가리킨다. obj는 이벤트가 발생한 컴포넌트, e는 부가 정보다. 주의: 자동 생성된 함수 이름을 바꿨다면 반드시 바뀐 이름으로 계속 작성해야 한다.

Event 설정 실습 예시 (onmouseenter)

Event 탭에서 onmouseenter 속성을 더블클릭하면 Script 창에 this.divMain_staLounge_onmouseenter = function(obj, e) {} 뼈대가 자동으로 생겨나고, 그 안에 원하는 동작(여기선 마우스가 올라오면 테두리를 파란색으로 바꾸는 코드)을 작성한다. 아래 화면은 다른 함수도 여러 개 함께 보여서 헷갈리기 쉬우므로, 방금 만든 divMain_staLounge_onmouseenter 함수와 오른쪽 Event 패널의 onmouseenter 속성을 빨간 박스로 표시했다.

Generate와 실행 방식(WRE/NRE)

화면 소스는 xfdl(XML)이라 브라우저가 바로 못 읽는다. Generate 과정을 거쳐 js로 변환해야 실행되며, 브라우저 위에서 도는 WRE와 별도 런타임으로 디바이스 API까지 쓸 수 있는 NRE 두 방식이 있다. 주의: js → xfdl로 역변환은 불가능하고, 변환된 js는 공통 프레임워크 파일 없이는 단독 실행되지 않는다.

Dataset을 만드는 두 가지 방법

컬럼과 데이터는 두 가지 방식으로 채울 수 있다. XML 소스를 직접 작성하거나, Dataset Editor에서 표처럼 하나씩 입력하면 된다. 결과는 같으니 편한 쪽을 쓰면 된다.

소스 방식: ColumnInfo/Rows를 XML 태그로 직접 작성한다. 코드를 붙여넣거나 대량 데이터를 다룰 때 편하다.

에디터 방식: Columns 표에서 컬럼을 정의하고 Rows 표에 값을 하나씩 입력한다. 아래 Dataset/Source 탭으로 두 화면을 오갈 수 있다.

개념과 바인딩

Dataset은 화면에 보이지 않는 표 형태의 데이터 그릇이다. 그 자체로는 아무것도 안 보이고, Grid 등과 binddataset 속성(또는 셀 단위 바인딩)으로 연결돼야 화면에 표시된다.

데이터 조회/검색

getRowCount()/getColumn(행, 컬럼)으로 기본 조회를 하고, findRow(단일 조건, 첫 매치 행만, 없으면 -1)와 findRowExpr(복합 조건식)로 원하는 행을 찾는다. 조건에 맞는 행을 전부 뽑고 싶으면 extractRows로 인덱스 배열을 한 번에 받는다.

정렬과 필터

keystring에 "S:+컬럼/-컬럼" 형태로 넣으면 정렬된다. filter("조건식")은 데이터를 지우는 게 아니라 화면 표시만 걸러내며, filter("")로 다시 해제한다.

추가·수정·삭제(CRUD)

addRow/insertRow + setColumn으로 행을 추가하고, setColumn으로 값을 고치면(원본값은 getOrgColumn으로 확인 가능) 상태가 바뀐다. deleteRow/deleteMultiRows로 삭제하며, getRowType으로 각 행의 상태(1정상·2추가·4수정·8삭제)를 확인할 수 있다. 주의: 이 모든 조작은 화면 메모리상의 값만 바꾸는 것이라, 서버(DB)에는 별도로 전송해야 반영된다.

초기화·복사·이벤트

reset()은 처음 불러온 상태로 되돌리고, clearData()는 완전히 비운다. copyData/copyRow로 다른 Dataset과 데이터를 주고받을 수 있다. cancolumnchange(변경 직전, false 반환 시 취소 가능)·oncolumnchanged(변경 직후) 이벤트로 값 변경을 감시·검증할 수 있다.

Calendar 컴포넌트는 dateformat으로 화면에 보여줄 형식을, editformat으로 실제 입력·편집할 때 쓸 형식을 각각 지정한다. yyyy(연도)·MM(월)·dd(일) 같은 형식 문자를 조합해 원하는 표기로 자유롭게 바꿀 수 있다.

형식 문자 한 줄 설명

yyyy : 연도 4자리

MM : 월 2자리

dd : 일 2자리

ddd : 요일

Theme을 쓰는 이유

넥사크로는 컴포넌트 하나하나에 개별적으로 스타일을 만들지 않고, Theme을 프로젝트 전체에 적용하는 방식을 쓴다. 그래서 화면마다·컴포넌트마다 매번 스타일을 새로 지정해주는 번거로움이 줄어든다.

두 종류의 Theme: NexacroTheme vs Theme

Resource Explorer에는 두 종류의 테마가 있다. NexacroTheme(확장자 .xtheme)은 style과 image가 하나로 합쳐진 압축 형태라 삭제·수정 같은 편집이 불가능하다. Theme은 style과 image가 분리되어 있어 자유롭게 편집할 수 있다.

NexacroTheme .xtheme

style + image

style과 image가 하나로 합쳐져 있어 편집 불가(삭제·수정 불가)

Theme

style image

style·image가 분리되어 있어 자유롭게 편집 가능

Theme의 XCSS에서 자주 쓰는 스타일 속성들이다. 자세한 문법은 필요할 때 하나씩 찾아 쓰면 되고, 여기서는 "이런 속성이 있다"는 것만 정리한다.

border : 테두리 설정

background : 배경 설정

bg-image : 배경 이미지 설정

linear-gradient : 그라데이션

font : 폰트 설정

box-shadow : 그림자 설정

background와 Inner Form

Div 컴포넌트의 background 속성을 빨간색이나 파란색으로 바꿔도 실제 화면에는 그 색이 나타나지 않는 경우가 있다. 그 이유는 Div 위에 눈에 보이지 않는 "Inner Form"이라는 내부 폼이 하나 더 겹쳐져 있기 때문으로, Div 안에 Button 같은 컴포넌트를 추가하면 실제로는 Div 바로 위가 아니라 이 Inner Form 위에 배치되는 구조다. 그래서 Div 자체에 배경 스타일을 제대로 주려면 Properties에서 직접 background를 바꾸는 대신, cssclass(예: .Div.div_blue { background: #0000ff; })로 클래스를 만들어 그 클래스를 Div 컴포넌트의 cssclass 속성에 연결해줘야 한다. 클래스만 만들어 놓고 컴포넌트에 연결하지 않으면 스타일이 적용되지 않는다는 점도 주의해야 한다.

옅은 파란 배경 전체가 cssclass로 스타일을 준 Div 영역이고, 그 안의 청록색 Button00은 Div 위의 Inner Form에 올라간 컴포넌트다.

Div 안에 컴포넌트를 넣으면 스크립트도 한 단계 더 들어간다

Div 위에 놓은 컴포넌트는 Inner Form 위에 배치되기 때문에, 코드에서 접근할 때는 div00.form.컴포넌트id처럼 한 단계 더 들어가야 한다. 이벤트를 더블클릭해 자동 생성되는 핸들러 함수 이름에도 같은 원리로 Div 이름이 한 단계 더 붙는다. 예를 들어 Div00 안의 Button00을 더블클릭해 onclick 핸들러를 만들면, Form에 바로 놓은 컴포넌트와 달리 함수 이름이 this.Div00_Button00_onclick = function(obj, e) {}처럼 "Div이름_컴포넌트이름" 형태로 생성된다.

Div에 url로 다른 화면 가지고 오기

Div는 url 속성에 다른 화면(xfdl) 경로를 지정해두면, 그 화면의 내용을 그대로 가져와 Div 안에 끼워 넣어 보여준다. 아래는 Div00의 url을 "Work::Work_formsev.xfdl"로 지정해, 그 화면의 "팝업창" 내용이 빨간 테두리로 표시된 Div 영역 안에 그대로 로드된 예시다.

넥사크로에는 "새 창"이 없다

브라우저의 새 창(window.open)과 달리 넥사크로에는 새 창을 띄우는 기능 자체가 없다. 그래서 팝업이 필요할 때는 스크립트로 ChildFrame을 만들어 화면 위에 겹쳐 띄우는 방식으로 구현한다.

Modal vs Modaless

Modal

팝업이 떠 있는 동안 mainframe(부모 화면)을 사용할 수 없다. 실무에서 주로 사용하는 방식.

Modaless

부모 화면을 계속 조작할 수 있는 대신, 좌표를 직접 계산해서 띄워야 한다.

Modal 팝업 예시 — 여는 스크립트

버튼을 클릭하면 ChildFrame을 만들어 Modal로 띄우는 스크립트다. edt00·edt01에 입력된 값을 param 딕셔너리로 묶어 팝업에 함께 넘긴다.

실행 결과

Modal 팝업이 떠 있는 동안에는 뒤의 mainframe이 어둡게 처리되며 조작할 수 없다.

ChildFrame 생성자 — id·top·left·width·height

부모 화면에서 new ChildFrame(id, top, left, width, height) 형태로 자식 프레임(팝업)을 만든다. 매개변수는 왼쪽부터 순서대로 id·top·left·width·height다.

new ChildFrame("popup1", 0, 0, 300, 400)

2

top — 0

3

left — 0

4

width — 300

5

height — 400

formurl·openalign — 어떤 화면을, 어디에

만들어진 ChildFrame에 formurl로 팝업창에 띄울 화면(xfdl) 파일을 연결하고, openalign으로 팝업창이 나타날 위치("center middle" 등)를 지정한다.

showModal() — 부모 → 자식으로 데이터 전달

팝업을 실제로 띄우는 메소드는 showModal()이며, 매개변수는 순서대로 다음과 같다.

objCF.showModal(this.getOwnerFrame(), param, this, "fn_popupCallback")

1

this.getOwnerFrame() — 팝업을 띄우는 부모 프레임

2

부모 → 자식으로 넘길 인자. 이 예시에서는 {userId: this.edt00.value, userName: this.edt01.value}처럼 딕셔너리로 묶어서 전달했다.

3

콜백 함수를 가진 객체 (보통 this)

4

팝업이 닫힌 뒤 실행할 콜백 함수 이름 — "fn_popupCallback"

close() — 자식 → 부모로 데이터 되돌려주기

반대로 팝업(자식) 화면에서 입력한 값을 부모 화면으로 되돌려줘야 할 때도 있다. 팝업 쪽 버튼에서 edt00·edt01 값을 읽어 ":"로 이어붙인 뒤 this.close(...)로 팝업을 닫으면서 값을 함께 넘긴다. close()에는 문자열 하나만 담을 수 있어서, 값이 여러 개면 이렇게 구분자로 이어붙여 보내야 한다.

콜백 함수 — 되돌아온 값 받기

부모 화면의 콜백 함수는 sPopupId(어떤 팝업이 닫혔는지)와 sReturn(close()로 넘어온 값)을 받는다. sPopupId로 어느 팝업인지 확인하고, sReturn을 split(":")으로 다시 나눠 각 입력창에 채워 넣는다. 주의: 통신은 비동기라 showModal() 바로 다음 줄에서 반환값을 읽으면 안 되고, 반드시 이 콜백 함수 안에서 처리해야 한다.

Modaless 팝업을 위한 준비 — Application 구조

넥사크로 화면은 Application > MainFrame > Form 순서로 구성된다. Modaless 팝업은 Modal과 달리 좌표를 직접 계산해서 띄워야 하는데, 그러려면 화면 크기의 기준이 되는 mainframe에 접근해야 하고, 그러려면 그 위 단계인 Application을 먼저 가져와야 한다.

Modaless 팝업 스크립트

nexacro.getApplication()으로 Application을 가져오고, mainframe.width/height로 메인 창의 크기를 읽는다. (전체 너비/높이 − 팝업 너비/높이)를 각각 2로 나누면 팝업을 정중앙에 둘 왼쪽(left)·위(top) 좌표가 나온다. 이렇게 구한 좌표는 화면 안에서의 상대 좌표이므로, system.clientToScreenX()/clientToScreenY()로 모니터 화면 기준 좌표로 바꿔줘야 실제로 화면에 배치할 수 있다.

주의: 이 예시의 nT 계산에는 objApp.mainframe.width가 두 번 쓰였다 — 세로 좌표이니 원래는 height여야 할 자리로 보이니, 실제로 쓸 때는 확인해보는 게 좋다.

실행 결과 — mainframe이 어두워지지 않는다

Modal과 달리 Modaless 팝업은 떠 있는 동안에도 뒤쪽 mainframe이 어두워지지 않고, 계속 조작할 수 있다.

tabjustify — 탭 너비

true로 두면 탭 버튼 너비가 전체 폭에 맞춰 균등하게 늘어나고, false(기본값)면 각 탭 이름의 글자 수만큼만 너비를 차지한다.

탭 페이지 추가·제거 — MDI에서 여러 업무 화면 관리(tabMdi)

MDI 방식에서 여러 업무 화면을 탭으로 전환하며 쓸 수 있게 해주는 것이 Tab 컴포넌트(tabMdi)다.

1

tabMdi.removeTabpage(0) — form_onload에서 디자인 시 기본으로 있던 0번째 빈 탭 제거

2

tabMdi.insertTabpage(id, -1, "", 텍스트) — 새 화면을 열 때 탭 추가 (인자 순서: 탭 ID · 삽입 위치(-1=맨 끝) · Form URL(비워두고 ChildFrame이 담당) · 탭에 표시할 텍스트)

3

tabMdi_onchanged — 탭 전환 시 발생. obj.tabpages[e.postindex].name으로 선택된 탭의 ID를 구해 avFrameWork[id].setFocus()로 해당 ChildFrame을 앞으로 가져온다

탭 닫기 버튼(showextrabutton)

1

2

tabMdi_onextrabuttonclick — 'x' 클릭 시 발생. 해당 ChildFrame의 form.close()로 화면을 닫고 obj.removeTabpage(e.index)로 탭도 함께 제거

정렬 버튼(fnArrange)

최대화·수평정렬·수직정렬·전체닫기 버튼을 누르면 버튼 id로 분기해서, 최대화/전체닫기는 직접 처리하고 나머지는 avFrameWork.arrange(정렬종류)로 넥사크로가 기본 제공하는 정렬 기능을 그대로 사용한다.

Frame 계열: VFrameSet·HFrameSet·FrameSet

하나의 애플리케이션을 상단 메뉴·좌측 메뉴·본문 작업 영역 등 여러 영역으로 나눌 때 Frame 계열 컴포넌트를 쓴다. VFrameSet은 하위 프레임을 위아래(세로)로, HFrameSet은 좌우(가로)로 배치하고, FrameSet은 좌표로 위치·크기를 직접 지정해 자유롭게 배치한다.

ChildFrame과 form 연결

화면 안에 실제 업무 화면을 띄우려면 ChildFrame 프레임 컴포넌트를 만들고, 그 위에 실제 form(.xfdl)을 연결해야 비로소 화면 내용이 보인다.

SDI vs MDI

애플리케이션 화면 구성 방식은 크게 두 가지다. SDI(Single Document Interface)는 한 번에 하나의 업무 화면만 표시하고, MDI(Multiple Document Interface)는 여러 업무 화면을 탭이나 창 형태로 동시에 열어둔다. 실무·실습에서는 MDI를 더 많이 쓴다.

Application_Desktop과 Add Frame

애플리케이션 레벨 화면인 Application_Desktop에서 이 Frame 배치 구조를 설정한다. mainframe에서 마우스 우클릭 후 "Add Frame"을 선택하면 하위 프레임을 추가할 수 있다.

separatesize 예시

각 FrameSet의 separatesize 속성은 하위 자식 프레임들의 크기(또는 비율)를 지정한다. 아래는 VFrameSet의 자식이 frameLogin·frameTop·HFrameSet 세 개일 때 separatesize를 "0,50,*"로 설정한 예시로, frameLogin은 0px(안 보임), frameTop은 50px 고정, HFrameSet은 나머지 공간을 모두 차지하도록 배치된다.

상단/좌측 메뉴 구성

상단 메뉴(frameTop)는 메뉴 정보를 담은 Dataset을 읽어 Button을 코드로 동적 생성하는 방식으로 만든다. 좌측 메뉴(frameLeft)에서 항목을 더블클릭하면 ChildFrame과 공통 틀 화면(frameWork)을 통해 실제 업무 화면을 불러오고, 동시에 frameMdi에 탭도 함께 추가된다.

반응형 로그인 화면

보이지 않는 기준 컴포넌트(가로·세로 50%)를 하나 두고, 로그인 박스를 그 기준점에서 자기 크기의 절반만큼 음수 오프셋으로 배치하면 창 크기가 바뀌어도 항상 정중앙을 유지한다.

참고

이 구조는 실무 프로젝트의 전체 골격을 짜는 설계 패턴이라 처음엔 복잡해 보일 수 있지만, "메뉴 Dataset → 동적 버튼/탭 생성 → ChildFrame으로 업무 화면 로드"라는 한 가지 흐름만 이해하면 대부분 응용할 수 있다.

Timer

setTimer(id, 주기)로 일정 간격마다 ontimer 이벤트를 반복 발생시키고, killTimer(id)로 멈춘다. 여러 타이머를 동시에 쓸 땐 e.timerid로 구분한다.

컴포넌트 동적 생성/제거

화면 디자인 시점에 미리 배치하지 않고, 스크립트로 실행 중에 컴포넌트를 새로 만들어 넣는 것을 동적 생성이라고 한다. 아래 스크립트에서 파란 박스가 생성 버튼, 빨간 박스가 제거 버튼의 코드다.

1

new Button(id, x, y, width, height) — 컴포넌트 객체 생성

2

this.addChild(id, obj) — Form의 자식으로 등록

3

obj.show() — 이 호출까지 있어야 실제 화면에 나타남

4

this.div02.form.addChild(...) — Div 내부(Inner Form)에도 같은 방식으로 동적 생성 가능

5

isValidObject(id) — 이미 존재하는지 먼저 확인(같은 id 중복 생성 방지)

6

obj.addEventHandler("onclick", 함수, this) — 동적 컴포넌트에 이벤트 핸들러 연결

7

this.removeChild(id) — Form에서 떼어냄 (동적 생성한 컴포넌트에만 사용)

8

obj.destroy() → obj = null — 완전히 파괴하고 변수를 비워 메모리 참조를 남기지 않음

실행 결과: 버튼을 클릭하면 노란 버튼이 새로 생겨나고, 다시 클릭하면 사라진다.

Global Function(gfn)

알림창, 팝업 열기, 공통 코드 조회처럼 여러 화면에서 반복되는 로직을 gfn 접두어 전역 함수(gfnAlert, gfnOpenPopup, gfnGetCommonCode 등)로 한 번만 만들어 공용으로 쓴다. 화면마다 같은 로직을 새로 짤 필요가 없고 문구·검증 규칙도 일관되게 유지된다.

WebView 연동

화면 안에 웹페이지를 띄울 땐 구형 WebBrowser 대신 WebView(Chromium 기반)를 쓴다. callScript()로 넥사크로에서 HTML 함수를 실행시키고, HTML 쪽은 FireUserNotify()로 데이터를 보내면 넥사크로의 onusernotify 이벤트에서 e.userdata로 받는다.

즐겨찾기(★) 처리

공통 틀 화면(frameWork)에 붙는 별 버튼으로, 전역 Dataset(gdsMyMenu)에 메뉴를 추가·삭제하는 방식으로 즐겨찾기를 구현한다.

1

this.getOwnerFrame().form의 param — 상위 ChildFrame이 전달해둔 값(menuid 등)을 꺼내 어떤 메뉴인지 확인

2

gdsMyMenu.findRow("MENU_ID", id) — 이미 즐겨찾기로 등록된 메뉴인지 확인, 등록되어 있으면 별 버튼 cssclass를 채워진 별로 표시

3

별 버튼 클릭 시 이미 즐겨찾기면 findRow 후 deleteRow()로 해제, 아니면 gdsMyMenu.addRow() + copyRow(...)로 전체 메뉴(gdsMenu)의 원본 행을 복사해 등록

Static 기준점으로 중앙 정렬

보이지 않는 기준 Static(예: staBase) 하나를 두고, 실제 내용을 그 기준점 대비 음수 오프셋으로 배치하는 방식이다.

1

기준 Static(staBase)의 left·top을 0으로, width·height를 화면의 50%로 설정 → 오른쪽 아래 꼭짓점이 항상 화면 정중앙

2

실제 내용 컴포넌트(예: divLogin, width 300·height 355)의 left·top을 staBase를 기준(anchor)으로 각각 -150·-177(자기 크기의 절반만큼 음수)로 지정

WebBrowser vs WebView

넥사크로에서 화면 안에 웹 페이지를 띄우는 컴포넌트는 두 가지다. 요즘은 Internet Explorer 자체를 더 이상 지원하지 않는 추세라, 실무·실습에서는 WebBrowser보다 WebView를 쓴다.

WebBrowser

Internet Explorer 엔진 기반. IE 자체가 더 이상 지원되지 않아 요즘은 잘 쓰지 않는다.

WebView

Microsoft Edge(Chromium 기반) 엔진. 실무·실습에서 주로 쓰는 최신 컴포넌트.

url 속성과 gfnGetServerUrl()

WebView의 url 속성에 주소를 지정하면 그 페이지가 화면 안에 로드된다. 서버 주소를 문자열로 직접 적지 않고, gfnGetServerUrl() 공통 함수를 호출해 현재 실행 환경(localhost·서버 IP·실제 배포 주소 등)에 맞는 웹 루트 경로를 동적으로 가져온 뒤, 그 뒤에 필요한 하위 경로를 이어붙여 최종 URL을 완성한다. 이렇게 하면 개발/테스트/운영 환경이 바뀌어도 소스 코드를 수정하지 않고 주소를 맞출 수 있다.

실행 결과

지정한 url의 웹 페이지가 WebView 컴포넌트 안에 그대로 로드된다.

서버 통신 개요

Web Server는 정적 자원을, WAS는 DB 조회 같은 동적 처리를 담당한다. 자바 쪽 조회 결과(RS, ResultSet)는 넥사크로가 바로 못 읽으므로 Dataset(DS) 형태로 변환하는 중간 모듈을 거쳐야 화면에 바인딩할 수 있다. 서버 쪽 데이터는 보통 VO·Map·List 형태인데, 이걸 넥사크로 Dataset과 서로 변환해주는 역할을 UiAdapter가 맡는다 — 값뿐 아니라 행의 추가/수정/삭제 상태까지 함께 변환한다.

transaction()의 6개 인자

순서대로 ① 요청 식별 이름, ② 서버 서비스 경로(URL), ③ 서버로 보낼 Dataset, ④ 서버에서 받아올 Dataset 매핑("화면Dataset=서버Dataset"), ⑤ 낱개 변수 파라미터, ⑥ 완료 후 실행할 콜백 함수명이다. 조회 결과 건수 등은 이 콜백 함수 안에서 확인해야 한다.

this.transaction("svcCheckUserId", "SvcUrl::user/checkUserId.do", "", "", "userId=" + nexacro.wrapQuote(userId), "fn_callback")

Sync/Async와 콜백의 중요성

넥사크로 기본 통신 방식은 비동기(Async)다. transaction() 호출 직후 다음 줄에서 바로 결과를 읽으면 아직 서버 응답이 도착하기 전이라, 방금 조회한 실제 값이 아니라 화면에 미리 넣어둔 샘플 값 등 엉뚱한 값을 보게 된다. 반드시 지정한 콜백 함수 안에서 결과를 처리해야 한다. 아래는 실제 콜백 함수 예시 — errCd가 음수면 실패로 보고 바로 알림 후 종료하고, 정상이면 svcId로 어떤 요청의 응답인지 구분해 분기 처리한다(빨간 박스 = 실패 처리 구간).

CORS와 NRE

브라우저는 동일 출처 정책(CORS)으로 화면 주소와 다른 도메인의 서버 요청을 막을 수 있다. 별도 실행기인 NRE로 실행하면 이 제약 없이 통신할 수 있어, 개발 중 테스트 때 자주 활용한다.

gfnTransaction() — 공통 래퍼 함수

transaction()과 인자 순서가 동일한 프로젝트 공통 함수로, 실무에서는 transaction()을 직접 쓰기보다 이렇게 감싸둔 공통 함수를 더 많이 쓴다.

this.gfnTransaction("svcGetNewBook", "user/getNewBook.do", "", "dsNewBook=dsNewBook", "", "fnCallback")

파라미터 문자열과 공백 문제

파라미터는 "key=값" 형태를 공백으로 이어붙여 전달하는데, 값 자체에 공백이 있으면(예: "홍 길동"처럼 띄어쓰기 있는 이름) 그 공백 지점에서 값이 잘려 "홍"까지만 전달되는 문제가 생긴다. 주의: nexacro.wrapQuote()로 값을 감싸야 공백이 있어도 안전하게 전달된다.

Before
"empName=" + sEmpName

After
"empName=" + nexacro.wrapQuote(sEmpName)

실제 조회 함수 예시 — deptCode는 그냥 붙이고, empName은 wrapQuote로 감싼 모습이다.

Dataset 전송 범위: :u vs :a

Dataset을 서버로 보낼 때 뒤에 붙이는 :u는 변경된(추가·수정·삭제) 데이터만, :a는 전체 데이터를 보낸다. 전송량을 줄이려면 :u를 주로 쓰며, 여러 Dataset을 동시에 보낼 땐 공백으로 나열한다(예: "in_emp=ds_emp in_aa=ds_dept"). 수정·삭제된 행은 바뀐 값뿐 아니라 수정 전 원래 값도 함께 보내지는데, 서버가 그 원래 값을 기준으로 WHERE절을 만들어야 정확히 그 행을 찾아 처리할 수 있기 때문이다.

URL을 별칭으로 관리(TypeDefinition-Services)

서버 주소를 코드에 직접 쓰지 않고 "EduUrl" 같은 PrefixID로 등록해두면 "EduUrl::save_emp.jsp"처럼 짧게 쓸 수 있다. 환경(개발/운영)이 바뀌어도 이 등록 값 한 곳만 고치면 돼서 유지보수가 쉬워진다. TypeDefinition-Services에는 두 종류가 있다: 넥사크로가 기본 제공하는 Resource Service(theme, imagerc, font 등 리소스 경로)와, 개발자가 직접 추가하는 User Service(EduUrl, SvcUrl 같은 서버 API 별칭).

3계층 구조와 MVC

서버는 Spring 기반 전자정부 프레임워크의 MVC 패턴을 따르며, 요청은 Controller → Service → Mapper → DB 순으로 내려가고 결과는 반대로 올라온다. 계층을 나누면 화면·로직·SQL이 서로 분리되어 유지보수가 쉬워진다.

Controller 작성 요소

@RequestMapping으로 요청 경로를 지정하고, 낱개 값은 @ParamVariable, Dataset 전체는 @ParamDataSet으로 받는다.

@RequestMapping(value="edu/getEmpList.do")
public NexacroResult getEmpList(
    @ParamVariable(name="deptCode") String deptCode) { ... }

NexacroResult로 응답 구성하기

Controller의 반환 타입은 NexacroResult다. 여기에 addDataSet()으로 목록 데이터를, addVariable()로 단일 값을 담아 반환하면 화면의 transaction 콜백에서 지정한 이름 그대로 받아볼 수 있다.

NexacroResult rst = new NexacroResult();
rst.addDataSet("outEmp", resultData);      // Dataset(목록) 응답
rst.addVariable("fvTotalCnt", totalCount); // 단일 값 응답
return rst;

실제 UserController 예시 — 파라미터 없이 조회해서 dsList란 이름의 Dataset으로 응답한다.

Service/Mapper 위임 구조

Controller는 직접 DB에 접근하지 않고 Service에 위임한다. Service는 인터페이스(예: NexaEduService)와 구현체(NexaEduServiceImpl)로 나뉘고, 구현체는 다시 Mapper 인터페이스(NexaEduMapper)를 호출한다. Mapper 인터페이스는 메서드 시그니처만 갖고 있고 실제 SQL은 짝을 이루는 Mapper.xml 파일에 있다. 아래는 회원 목록 조회(selectUserList) 하나가 Service 인터페이스 → ServiceImpl → Mapper 인터페이스 → Mapper.xml SQL까지 그대로 이름을 이어가며 내려가는 실제 예시다.

① UserService (인터페이스)

② UserServiceImpl (구현체) — Mapper로 그대로 위임

③ UserMapper (인터페이스)

④ Mapper.xml — 실제 SQL

RowType 분기 처리

저장 시에는 Dataset의 각 행에 자동 기록된 RowType(추가/수정/삭제 상태)을 확인해 insert/update/delete 메서드를 각각 분기 호출한다. 여러 상태의 행이 한 번에 섞여 들어와도 이 분기로 한 번의 저장 요청에서 모두 처리된다.

switch (row.get("DataSetRowType")) {
  case DataSet.ROW_TYPE_INSERTED: mapper.insertEmp(row); break;
  case DataSet.ROW_TYPE_UPDATED:  mapper.updateEmp(row); break;
  case DataSet.ROW_TYPE_DELETED:  mapper.deleteEmp(row); break;
}

파일 업로드 서버 처리

서버 Controller는 MultipartHttpServletRequest로 업로드 요청을 받는다. 지정된 저장 폴더가 없으면 File.mkdirs()로 새로 만들고, 같은 이름의 파일이 이미 있으면 날짜·시간을 붙인 새 파일명을 만들어 덮어쓰기를 막는다. transferTo()로 실제 디스크에 저장한 뒤, 저장된 파일 정보(FILE_ID·FILE_NAME·FILE_SIZE)를 새 행으로 담은 Dataset을 응답으로 돌려준다.

FileUpTransfer 클라이언트 흐름

화면 쪽에서는 FileUpTransfer00.upload(...)를 호출해 업로드를 실행하고, 성공하면 발생하는 onsuccess 이벤트의 e.datasets[0]에서 서버가 돌려준 파일 정보를 꺼낸다. 이 콜백 안에서 바로 다음 단계(예: 회원가입 완료 처리 함수)를 이어서 호출하는 체이닝 패턴이 자주 쓰인다 — 업로드할 파일이 없으면 이 단계를 건너뛰고 바로 다음 처리로 넘어가면 된다.

페이징 데이터 조회 흐름

화면에서 cnt(한 페이지 개수)·offset(시작 위치)을 파라미터로 보내면 서버가 그 구간만 조회해서 돌려준다. 전체 흐름은 화면 transaction(cnt, offset) → Controller → Service → Mapper → SQL 실행 → 결과가 역순으로 반환 → Controller가 NexacroResult에 목록+총건수를 담아 응답 → 콜백이 그리드·페이지 버튼을 갱신 순서다. 예를 들어 페이지 크기 5, offset=20이면 21~25번째 행만 조회해온다. 페이지 번호가 바뀔 때마다 offset만 다시 계산해서 재요청한다.

아이디 중복 체크 처리 패턴

화면이 입력된 아이디를 보내면 서버는 COUNT 쿼리로 결과를 fvIdCnt에 담아 돌려준다. 개수가 0보다 크면 errorCode 100 + "이미 등록된 아이디입니다" 메시지를, 0이면 errorCode 200(사용 가능)을 반환하는 식으로 에러코드 자체를 결과 판별에 활용하는 패턴이다.

로그인과 전역 Dataset(gdsUser)

로그인 성공 시 서버가 돌려준 사용자 정보를 gdsUser 같은 애플리케이션 전역 Dataset에 채워두면, 이후 어느 화면에서든 다시 서버에 묻지 않고 바로 꺼내 쓸 수 있다.

this.transaction("svcLoginUser", "SvcUrl::user/LoginUser.do", "", "gdsUser=gdsUser", "userId=" + ... + " pass=" + ..., "fn_callback")

로그인/회원 정보를 담는 실제 tb_user 테이블 구조 — USER_ID가 PK이고 PASS·USER_NAME·EMAIL 등은 대부분 NULL 허용이다.

파라미터 형태별 처리

문자열 하나만 넘어올 땐 이름이 없으므로 _parameter 예약어로 받아야 한다. 조건이 여러 개면 VO 클래스(예: NexaEduVo)로 묶어 parameterType="com.edupack.edu.vo.NexaEduVo"로 지정하고 필드명 그대로(#{deptCode}, #{empName}) 쓴다. Dataset을 그대로 넘길 땐 parameterType="map"으로 받아 Dataset 컬럼명(COL_DEPT 등)을 그대로 조건식에 쓴다.

#{ } 바인딩과 조건절 자동 처리

#{파라미터명}은 값을 SQL 인젝션 없이 안전하게 채워 넣는 문법이다. <if> 태그로 조건절 자체를 생략 가능하게 만들 수 있고, <where> 태그를 쓰면 조건이 하나라도 참일 때만 WHERE를 붙이고 불필요한 첫 AND도 자동으로 지워준다. 조건이 두 개 이상일 때 VO + <where>/<if>를 함께 쓰는 예시:

<select id="getEmpListParam2" parameterType="com.edupack.edu.vo.NexaEduVo" resultType="map">
  SELECT * FROM tbl_employees
  <where>
    <if test="deptCode != null and deptCode != ''">AND DEPT_CODE = #{deptCode}</if>
    <if test="empName != null and empName != ''">AND EMP_NAME = #{empName}</if>
  </where>
</select>

Mapper.xml 조회 SQL

하나의 Mapper.xml 안에 여러 <select id="..."> 태그를 두고 조건 유무·형태별로 SQL을 나눠 작성한다. 화면 Dataset 컬럼명과 맞추기 위해 AS로 별칭을 붙이는 경우가 많다 — 공통 코드처럼 분류/세부값 구조인 테이블도 같은 방식으로 별칭을 맞춰 조회한다.

SELECT DET_CODE AS CODE, DET_NAME AS NAME FROM tbl_common_code WHERE MST_CODE = 'POSITION'

Insert/Update/Delete 매퍼

<insert>/<update>/<delete> 태그로 각각 정의하며, update·delete는 대개 PK 컬럼(예: EMP_ID)을 WHERE 조건으로 사용한다. 서버 Service 단계의 RowType 분기와 짝을 이뤄, 저장 버튼 한 번으로 여러 행의 추가/수정/삭제가 한꺼번에 처리된다.

UPDATE tbl_employees SET EMP_NAME = #{EMP_NAME}, ... WHERE EMP_ID = #{EMP_ID}
DELETE FROM tbl_employees WHERE EMP_ID = #{EMP_ID}

중복체크·로그인 인증 SQL

아이디 중복 체크는 COUNT(*)로 존재 개수만 확인한다(0=사용 가능, 1 이상=이미 존재). 로그인은 아이디+비밀번호로 COUNT를 세어 성공 여부만 판단하는 방식과, 조건에 맞는 회원 정보를 통째로 조회하는 방식을 함께 쓴다 — 회원가입 저장 시에는 now()로 가입일시를 DB 서버 시각 기준으로 자동 기록한다.

-- 중복 체크
SELECT COUNT(*) FROM tb_user WHERE USER_ID = #{userId}

-- 로그인 (존재 여부 + 데이터 조회를 함께 씀)
SELECT COUNT(*) FROM tb_user WHERE USER_ID = #{userId} AND PASS = #{pass}
SELECT USER_ID, USER_NAME, EMAIL, TEL_NO, PROFILE FROM tb_user
  WHERE USER_ID = #{userId} AND PASS = #{pass}

ROW_NUMBER()와 LIMIT/OFFSET

ROW_NUMBER() OVER(ORDER BY ...)로 순번을 매기고, LIMIT/OFFSET으로 필요한 구간만 잘라온다. 화면에서 넘긴 cnt/offset 값을 그대로 #{cnt}/#{offset}에 바인딩하는 방식으로 페이지마다 다른 구간을 조회하며, 전체 건수는 별도의 COUNT 쿼리로 함께 가져와 페이지 버튼 개수를 계산하는 데 쓴다.

<select id="getPageData" parameterType="map" resultType="map">
  SELECT ROW_NUMBER() OVER(ORDER BY ID ASC) AS ROW_NUM, ID, NAME, DESCRIPTION, USE_YN, REG_USER
  FROM tbl_sample
  ORDER BY ID ASC
  LIMIT #{cnt} OFFSET #{offset}
</select>

<select id="getTotalCount" resultType="int">
  SELECT COUNT(*) AS totalcnt FROM tbl_sample
</select>

공통 코드 테이블 설계

직급·부서·취미처럼 자주 안 바뀌는 코드들을 각각 테이블로 만들지 않고, MST_CODE(분류)·DET_CODE(세부값) 구조의 공통 코드 테이블(tbl_common_code) 하나로 모아 관리한다 — 예를 들어 MST_CODE=POSITION 그룹 안에 10=대표이사, 20=이사, 30=부장처럼 DET_CODE/DET_NAME 쌍이 나열되는 식이다. 앱 시작 시 한 번만 전역으로 조회해두면 불필요한 서버 통신을 줄일 수 있다.

투비소프트와 넥사크로

투비소프트는 기업용 업무 화면(UI) 솔루션을 만드는 회사이고, 넥사크로는 그 화면을 만드는 개발 도구다. IDE인 NEXACRO Studio로 화면을 만들면 .xfdl 파일이 생성된다.

프로젝트 생성 절차

New로 새 프로젝트를 만들 때 이름/경로, 대상 디바이스, 초기 화면 구성을 순서대로 지정한다. 생성되는 프로젝트에는 Environment, TypeDefinition(Objects·Services), Application Information 같은 설정 항목이 기본으로 함께 만들어진다.

Project Explorer vs Resource Explorer

Project Explorer는 환경설정·컴포넌트 정보·서비스 경로 같은 프로젝트 구조를 담고, Resource Explorer는 Theme 등 디자인 리소스를 담는다. Form에 컴포넌트를 추가하면 관련 디자인 요소가 자동으로 Resource Explorer에 반영된다.

외부 Theme 폴더 가져오기

Resource Explorer에서 "Open Theme Folder"로 실제 저장 경로를 연 뒤 폴더를 복사해 넣는다. 주의: 외부에서 직접 복사한 파일은 자동 인식되지 않으므로 반드시 Refresh를 해줘야 프로젝트에 반영된다.

외부 화면 폴더 가져오기

CompGuide 같은 외부 폼 폴더는 단순히 복사만 해서는 인식되지 않는다. TypeDefinition의 Services에 이름·경로·타입(form)을 등록해야 그 폴더의 화면을 실제로 쓸 수 있다.

Nexacro N Reference Guide

Help 메뉴의 이 도움말에서 컴포넌트별 속성·메소드·이벤트뿐 아니라 내부 구조(Control Map)까지 확인할 수 있어, 세부 스타일을 지정하기 전에 어떤 하위 요소가 있는지 미리 파악하기 좋다.

mainframe 크기 설정

Application Information의 mainframe 속성에서 전체 창의 width/height, 정렬 방식을 설정한다. 이 값은 Modaless 팝업을 화면 정중앙에 계산해 띄울 때 기준으로 쓰인다.

.xjs/.xfdl과 Generate

.xjs 파일은 실제로는 XML 안에 스크립트를 담은 형식이다. 브라우저에서 실행하려면 Generate 과정을 거쳐 xfdl/xjs를 실제 js 파일로 변환해야 한다.

Local Web Server의 한계

스튜디오 내장 Local Web Server는 실제 백엔드에 연결되어 있지 않아 화면·레이아웃 확인용으로만 적합하다. 서버 데이터 연동까지 확인하려면 실제 Web Server(Tomcat 등)로 실행해야 한다.

webapp 폴더와 Generate Path

Java 웹 프로젝트의 src/main/webapp이 실제 웹 주소의 루트가 된다. Generate Path를 이 webapp 하위 경로로 맞춰두면 변환된 결과물이 곧바로 서버가 읽을 수 있는 위치에 생성된다.

QuickView로 실서버 테스트

Run Environment를 Web Server로 바꾸고 실제 톰캣 주소를 지정하면, Generate된 결과물이 진짜 서버를 통해 로드되어 데이터 조회·수정까지 정상 테스트할 수 있다.

Application 추가와 Frame Template

Application Information에서 새 Application을 추가할 때 Frame Template을 "Full"로 두면 화면 전체를 채우는 기본 골격(Form_Work.xfdl)이 자동 생성되어, 매번 빈 화면부터 짤 필요가 없다.

전역 Dataset과 화면 계층 설계

로그인 정보처럼 앱 전체가 공유할 데이터는 전역 Dataset(gdsUser 등)에 두고, 하나의 뼈대 화면 안에서 상황에 따라 필요한 하위 화면(로그인/회원가입 등)만 바꿔 끼우는 구조로 설계하면 화면 간 연결을 이해하기 쉬워진다.

MDI 프레임 구조 요약

frameTop(상단 메뉴)·frameLeft(좌측 메뉴)·frameMdi(탭 관리)·frameWork(업무 화면 공통 틀)이 서로 맞물려 하나의 MDI 애플리케이션 골격을 이룬다. 각 프레임의 자세한 구현은 "넥사크로 소개" 쪽 Frame 구조 항목을 함께 참고하면 좋다.
