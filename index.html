넥사크로(Nexacro)가
무엇인지부터 정리한다

넥사크로는 (주)투비소프트가 만든 국산 RIA(Rich Internet Application) 개발 플랫폼입니다. 공공기관, 금융권, 대기업 SI 프로젝트의 화면 개발 표준으로 널리 쓰이고 있어서, 전문가 양성 과정을 준비하며 배운 내용을 이 페이지에 순서대로 정리해두려고 합니다.

실무 SI 표준

공공/금융 SI 프로젝트에서 화면 개발 표준 툴로 채택되는 경우가 많아 취업 실무와 바로 연결됩니다.

컴포넌트 기반 개발

Grid, Div, Dataset 등 컴포넌트 단위 개발 방식을 익히면 다른 RIA/UI 프레임워크 이해에도 도움이 됩니다.

데이터셋 중심 구조

화면과 서버 통신을 Dataset이 매개하는 구조라, 데이터 바인딩 개념을 확실히 잡아둘 필요가 있습니다.

넥사크로의 특징

스크립트 + 컴포넌트 결합 구조

화면(Form)에 컴포넌트를 배치하고, 각 컴포넌트의 이벤트에 JavaScript 유사 문법의 스크립트를 붙이는 방식으로 동작을 구현합니다. Nexacro Studio의 스크립트 에디터에서 직접 로직을 작성합니다.

화면에서 서버로 데이터를 보내고, Controller·Mapper 등을 거쳐 처리한 뒤 다시 화면으로 돌려받는 전체 흐름을 도식화하면 다음과 같다.

1

화면 (클라이언트)

this.transaction()으로 서비스 URL을 호출하며 요청 Dataset을 함께 전송

2

Controller

요청을 받아 어떤 서비스 로직으로 넘길지 라우팅

3

Service / Mapper (SQL 실행)

MyBatis Mapper의 SQL을 실행해 DB를 조회·처리

4

DB

조회·처리 결과를 Service/Mapper로 반환

5

화면 (클라이언트) — 응답

처리 결과를 Dataset(PDF/XML)으로 응답받아 화면을 갱신

코드 예시

// 클라이언트: 서비스 호출
this.transaction(
  "svcMemberList=member.list",
  "ds_search=input", "ds_member=output", "",
  this.cb_search, ""
);
// 서버: 요청 Dataset을 받아 조회 결과를 응답 Dataset에 채움
public void memberList(PlatformData reqPd, PlatformData resPd) {
  DataSet dsSearch = reqPd.getDataSet("ds_search");
  DataSet dsMember = resPd.newDataSet("ds_member");
  // dsSearch 조건으로 SQL 실행 후 dsMember에 결과 매핑
}

서비스에서 Mapper를 호출한 뒤 MyBatis가 XML 속 SQL을 찾아 실행하고 결과를 매핑해 돌려주기까지의 흐름을 도식화하면 다음과 같다.

1

서비스 코드 — Mapper 호출

예: sqlSession.selectList("selectMemberList", params)

2

MyBatis — 매퍼 XML 탐색

호출한 id와 일치하는 <select> 구문을 찾음

3

파라미터 바인딩

#{ } 자리에 전달받은 값이 채워져 최종 SQL 완성

4

DB 실행

완성된 SQL이 DB에서 실행되어 결과 Row들을 반환

5

결과 매핑 — 응답

resultType(hashmap 등) 기준으로 컬럼 별칭(alias)에 맞춰 매핑되어 반환

코드 예시

<select id="selectMemberList" resultType="hashmap">
  SELECT
    member_id   AS id,
    member_name AS name,
    age
  FROM member
  WHERE dept_cd = #{deptCd}
  ORDER BY member_id
</select>

클라이언트가 토픽을 등록해 두면, 백엔드가 공급한 메시지를 X-PUSH 서버가 매칭해서 해당 사용자에게만 밀어준다. 전체 흐름을 도식화하면 다음과 같다.

1

Nexacro Client — 접속과 토픽 등록

connect()로 접속한 뒤 registerTopic() / subscribe()로 받고 싶은 TOPIC을 등록하고 대기

2

Back End — Message Provider

Provider API로 'TOPIC + 메시지'를 생성해 X-PUSH 서버에 공급(sendPushMessage)

3

X-PUSH Server — 매칭과 보관

TOPIC TYPE/ID가 맞는 사용자를 찾아 전달. 신뢰성 메시지는 T_MESSAGE·T_USER_MESSAGE에 저장해 두었다가 못 받은 사람에게 다시 보냄

4

Nexacro Client — 수신과 파싱

X-PUSH Object가 Message Layout(XML) 기준으로 메시지를 해석해 Dataset에 반영

5

수신 확인 — 신뢰성 메시지만

ackn(엔진 응답)과 responseMessage()(수신 확인)를 보내면 MESSAGE_STATE가 0에서 2로 바뀜

코드 예시

// 백엔드(Provider): 메시지 공급
pushMessage.setActionType(Constants.ACTION_RELI_STRING); // 신뢰성
pushMessage.setTopicType("NOTI");  // 반드시 4byte
pushMessage.setTopicId("ALL");
pushMessage.addData("100");
pushMessage.addData("새로운 메시지가 도착했습니다.");
provider.sendPushMessage(pushMessage);
<!-- 클라이언트: Message Layout — 필드 개수를 Provider와 맞춰야 함 -->
<message type="1000">
  <field id="TOPIC_ID"   type="string" size="9" key="true"/>
  <field id="TOPIC_TYPE" type="string" size="255"/>
  <field id="CODE"       type="string" size="255"/>

</message>

이벤트 핸들러 & 함수 문법

이벤트를 더블클릭하면 핸들러 함수가 자동 생성된다. this.함수명 = function(obj, e) {} 형태(함수 표현식)를 압도적으로 많이 쓰며, this는 그 스크립트가 속한 Form 자신을 가리킨다. obj는 이벤트가 발생한 컴포넌트, e는 부가 정보다. 주의: 자동 생성된 함수 이름을 바꿨다면 반드시 바뀐 이름으로 계속 작성해야 한다.

Event 설정 실습 예시 (onmouseenter)

Event 탭에서 onmouseenter 속성을 더블클릭하면 Script 창에 this.divMain_staLounge_onmouseenter = function(obj, e) {} 뼈대가 자동으로 생겨나고, 그 안에 원하는 동작(여기선 마우스가 올라오면 테두리를 파란색으로 바꾸는 코드)을 작성한다. 아래 화면은 다른 함수도 여러 개 함께 보여서 헷갈리기 쉬우므로, 방금 만든 divMain_staLounge_onmouseenter 함수와 오른쪽 Event 패널의 onmouseenter 속성을 빨간 박스로 표시했다.

Generate와 실행 방식(WRE/NRE)

화면 소스는 xfdl(XML)이라 브라우저가 바로 못 읽는다. Generate 과정을 거쳐 js로 변환해야 실행되며, 브라우저 위에서 도는 WRE와 별도 런타임으로 디바이스 API까지 쓸 수 있는 NRE 두 방식이 있다. 주의: js → xfdl로 역변환은 불가능하고, 변환된 js는 공통 프레임워크 파일 없이는 단독 실행되지 않는다.

Dataset을 만드는 두 가지 방법

컬럼과 데이터는 두 가지 방식으로 채울 수 있다. XML 소스를 직접 작성하거나, Dataset Editor에서 표처럼 하나씩 입력하면 된다. 결과는 같으니 편한 쪽을 쓰면 된다.

소스 방식: ColumnInfo/Rows를 XML 태그로 직접 작성한다. 코드를 붙여넣거나 대량 데이터를 다룰 때 편하다.

에디터 방식: Columns 표에서 컬럼을 정의하고 Rows 표에 값을 하나씩 입력한다. 아래 Dataset/Source 탭으로 두 화면을 오갈 수 있다.

개념과 바인딩

Dataset은 화면에 보이지 않는 표 형태의 데이터 그릇이다. 그 자체로는 아무것도 안 보이고, Grid 등과 binddataset 속성(또는 셀 단위 바인딩)으로 연결돼야 화면에 표시된다.

데이터 조회/검색

getRowCount()/getColumn(행, 컬럼)으로 기본 조회를 하고, findRow(단일 조건, 첫 매치 행만, 없으면 -1)와 findRowExpr(복합 조건식)로 원하는 행을 찾는다. 조건에 맞는 행을 전부 뽑고 싶으면 extractRows로 인덱스 배열을 한 번에 받는다.

정렬과 필터

keystring에 "S:+컬럼/-컬럼" 형태로 넣으면 정렬된다. filter("조건식")은 데이터를 지우는 게 아니라 화면 표시만 걸러내며, filter("")로 다시 해제한다.

추가·수정·삭제(CRUD)

addRow/insertRow + setColumn으로 행을 추가하고, setColumn으로 값을 고치면(원본값은 getOrgColumn으로 확인 가능) 상태가 바뀐다. deleteRow/deleteMultiRows로 삭제하며, getRowType으로 각 행의 상태(1정상·2추가·4수정·8삭제)를 확인할 수 있다. 주의: 이 모든 조작은 화면 메모리상의 값만 바꾸는 것이라, 서버(DB)에는 별도로 전송해야 반영된다.

초기화·복사·이벤트

reset()은 처음 불러온 상태로 되돌리고, clearData()는 완전히 비운다. copyData/copyRow로 다른 Dataset과 데이터를 주고받을 수 있다. cancolumnchange(변경 직전, false 반환 시 취소 가능)·oncolumnchanged(변경 직후) 이벤트로 값 변경을 감시·검증할 수 있다.

그룹핑과 소계

셀 병합·서프레스·기타

Merge Cells는 셀을 완전히 하나로 합치고, Having child cells는 겉만 합치고 내부 subcell을 유지한다. suppress는 반복되는 값을 자동으로 병합 표시해준다. getCellProperty/setCellProperty로 실행 중 셀 속성을 읽고 바꿀 수 있고, 페이징은 서버에서 offset/개수만큼 끊어 받아온 뒤 공통 함수로 페이지 버튼을 그려주는 방식으로 구현한다.

Calendar 컴포넌트는 dateformat으로 화면에 보여줄 형식을, editformat으로 실제 입력·편집할 때 쓸 형식을 각각 지정한다. yyyy(연도)·MM(월)·dd(일) 같은 형식 문자를 조합해 원하는 표기로 자유롭게 바꿀 수 있다.

형식 문자 한 줄 설명

yyyy : 연도 4자리

MM : 월 2자리

dd : 일 2자리

ddd : 요일

예: dateformat을 "yyyy-MM-dd ddd"로 두면 "2026-07-25 토"처럼 요일까지 표시되고, editformat을 "yyyy-MM-dd"로 두면 실제 입력값은 요일 없이 저장된다.

Theme을 쓰는 이유

넥사크로는 컴포넌트 하나하나에 개별적으로 스타일을 만들지 않고, Theme을 프로젝트 전체에 적용하는 방식을 쓴다. 그래서 화면마다·컴포넌트마다 매번 스타일을 새로 지정해주는 번거로움이 줄어든다.

두 종류의 Theme: NexacroTheme vs Theme

Resource Explorer에는 두 종류의 테마가 있다. NexacroTheme(확장자 .xtheme)은 style과 image가 하나로 합쳐진 압축 형태라 삭제·수정 같은 편집이 불가능하다. Theme은 style과 image가 분리되어 있어 자유롭게 편집할 수 있다.

NexacroTheme .xtheme

style + image

style과 image가 하나로 합쳐져 있어 편집 불가(삭제·수정 불가)

Theme

background와 Inner Form

Div 컴포넌트의 background 속성을 빨간색이나 파란색으로 바꿔도 실제 화면에는 그 색이 나타나지 않는 경우가 있다. 그 이유는 Div 위에 눈에 보이지 않는 "Inner Form"이라는 내부 폼이 하나 더 겹쳐져 있기 때문으로, Div 안에 Button 같은 컴포넌트를 추가하면 실제로는 Div 바로 위가 아니라 이 Inner Form 위에 배치되는 구조다. 그래서 Div 자체에 배경 스타일을 제대로 주려면 Properties에서 직접 background를 바꾸는 대신, cssclass(예: .Div.div_blue { background: #0000ff; })로 클래스를 만들어 그 클래스를 Div 컴포넌트의 cssclass 속성에 연결해줘야 한다. 클래스만 만들어 놓고 컴포넌트에 연결하지 않으면 스타일이 적용되지 않는다는 점도 주의해야 한다.

옅은 파란 배경 전체가 cssclass로 스타일을 준 Div 영역이고, 그 안의 청록색 Button00은 Div 위의 Inner Form에 올라간 컴포넌트다.

Div 안에 컴포넌트를 넣으면 스크립트도 한 단계 더 들어간다

Div 위에 놓은 컴포넌트는 Inner Form 위에 배치되기 때문에, 코드에서 접근할 때는 div00.form.컴포넌트id처럼 한 단계 더 들어가야 한다. 이벤트를 더블클릭해 자동 생성되는 핸들러 함수 이름에도 같은 원리로 Div 이름이 한 단계 더 붙는다. 예를 들어 Div00 안의 Button00을 더블클릭해 onclick 핸들러를 만들면, Form에 바로 놓은 컴포넌트와 달리 함수 이름이 this.Div00_Button00_onclick = function(obj, e) {}처럼 "Div이름_컴포넌트이름" 형태로 생성된다.

Div에 url로 다른 화면 가지고 오기

Div는 url 속성에 다른 화면(xfdl) 경로를 지정해두면, 그 화면의 내용을 그대로 가져와 Div 안에 끼워 넣어 보여준다. 아래는 Div00의 url을 "Work::Work_formsev.xfdl"로 지정해, 그 화면의 "팝업창" 내용이 빨간 테두리로 표시된 Div 영역 안에 그대로 로드된 예시다.

넥사크로에는 "새 창"이 없다

브라우저의 새 창(window.open)과 달리 넥사크로에는 새 창을 띄우는 기능 자체가 없다. 그래서 팝업이 필요할 때는 스크립트로 ChildFrame을 만들어 화면 위에 겹쳐 띄우는 방식으로 구현한다.

Modal vs Modaless

Modal

팝업이 떠 있는 동안 mainframe(부모 화면)을 사용할 수 없다. 실무에서 주로 사용하는 방식.

Modaless

부모 화면을 계속 조작할 수 있는 대신, 좌표를 직접 계산해서 띄워야 한다.

Modal 팝업 예시 — 여는 스크립트

버튼을 클릭하면 ChildFrame을 만들어 Modal로 띄우는 스크립트다. edt00·edt01에 입력된 값을 param 딕셔너리로 묶어 팝업에 함께 넘긴다.

반대로 팝업(자식) 화면에서 입력한 값을 부모 화면으로 되돌려줘야 할 때도 있다. 팝업 쪽 버튼에서 edt00·edt01 값을 읽어 ":"로 이어붙인 뒤 this.close(...)로 팝업을 닫으면서 값을 함께 넘긴다. close()에는 문자열 하나만 담을 수 있어서, 값이 여러 개면 이렇게 구분자로 이어붙여 보내야 한다.

콜백 함수 — 되돌아온 값 받기

부모 화면의 콜백 함수는 sPopupId(어떤 팝업이 닫혔는지)와 sReturn(close()로 넘어온 값)을 받는다. sPopupId로 어느 팝업인지 확인하고, sReturn을 split(":")으로 다시 나눠 각 입력창에 채워 넣는다. 주의: 통신은 비동기라 showModal() 바로 다음 줄에서 반환값을 읽으면 안 되고, 반드시 이 콜백 함수 안에서 처리해야 한다.

넥사크로 화면은 Application > MainFrame > Form 순서로 구성된다. Modaless 팝업은 Modal과 달리 좌표를 직접 계산해서 띄워야 하는데, 그러려면 화면 크기의 기준이 되는 mainframe에 접근해야 하고, 그러려면 그 위 단계인 Application을 먼저 가져와야 한다.

Frame 계열: VFrameSet·HFrameSet·FrameSet

하나의 애플리케이션을 상단 메뉴·좌측 메뉴·본문 작업 영역 등 여러 영역으로 나눌 때 Frame 계열 컴포넌트를 쓴다. VFrameSet은 하위 프레임을 위아래(세로)로, HFrameSet은 좌우(가로)로 배치하고, FrameSet은 좌표로 위치·크기를 직접 지정해 자유롭게 배치한다.

ChildFrame과 form 연결

화면 안에 실제 업무 화면을 띄우려면 ChildFrame 프레임 컴포넌트를 만들고, 그 위에 실제 form(.xfdl)을 연결해야 비로소 화면 내용이 보인다.

SDI vs MDI

애플리케이션 화면 구성 방식은 크게 두 가지다. SDI(Single Document Interface)는 한 번에 하나의 업무 화면만 표시하고, MDI(Multiple Document Interface)는 여러 업무 화면을 탭이나 창 형태로 동시에 열어둔다. 실무·실습에서는 MDI를 더 많이 쓴다.

Application_Desktop과 Add Frame

애플리케이션 레벨 화면인 Application_Desktop에서 이 Frame 배치 구조를 설정한다. mainframe에서 마우스 우클릭 후 "Add Frame"을 선택하면 하위 프레임을 추가할 수 있다.

separatesize 예시

각 FrameSet의 separatesize 속성은 하위 자식 프레임들의 크기(또는 비율)를 지정한다. 아래는 VFrameSet의 자식이 frameLogin·frameTop·HFrameSet 세 개일 때 separatesize를 "0,50,*"로 설정한 예시로, frameLogin은 0px(안 보임), frameTop은 50px 고정, HFrameSet은 나머지 공간을 모두 차지하도록 배치된다.

상단/좌측 메뉴 구성

상단 메뉴(frameTop)는 메뉴 정보를 담은 Dataset을 읽어 Button을 코드로 동적 생성하는 방식으로 만든다. 좌측 메뉴(frameLeft)에서 항목을 더블클릭하면 ChildFrame과 공통 틀 화면(frameWork)을 통해 실제 업무 화면을 불러오고, 동시에 frameMdi에 탭도 함께 추가된다.

반응형 로그인 화면

보이지 않는 기준 컴포넌트(가로·세로 50%)를 하나 두고, 로그인 박스를 그 기준점에서 자기 크기의 절반만큼 음수 오프셋으로 배치하면 창 크기가 바뀌어도 항상 정중앙을 유지한다.

참고

이 구조는 실무 프로젝트의 전체 골격을 짜는 설계 패턴이라 처음엔 복잡해 보일 수 있지만, "메뉴 Dataset → 동적 버튼/탭 생성 → ChildFrame으로 업무 화면 로드"라는 한 가지 흐름만 이해하면 대부분 응용할 수 있다.

Timer

setTimer(id, 주기)로 일정 간격마다 ontimer 이벤트를 반복 발생시키고, killTimer(id)로 멈춘다. 여러 타이머를 동시에 쓸 땐 e.timerid로 구분한다.

컴포넌트 동적 생성/제거

화면 디자인 시점에 미리 배치하지 않고, 스크립트로 실행 중에 컴포넌트를 새로 만들어 넣는 것을 동적 생성이라고 한다. 아래 스크립트에서 파란 박스가 생성 버튼, 빨간 박스가 제거 버튼의 코드다.

1

new Button(id, x, y, width, height) — 컴포넌트 객체 생성

2

this.addChild(id, obj) — Form의 자식으로 등록

3

obj.show() — 이 호출까지 있어야 실제 화면에 나타남

4

this.div02.form.addChild(...) — Div 내부(Inner Form)에도 같은 방식으로 동적 생성 가능

5

isValidObject(id) — 이미 존재하는지 먼저 확인(같은 id 중복 생성 방지)

6

obj.addEventHandler("onclick", 함수, this) — 동적 컴포넌트에 이벤트 핸들러 연결

7

8

실행 결과: 버튼을 클릭하면 노란 버튼이 새로 생겨나고, 다시 클릭하면 사라진다.

Global Function(gfn)

알림창, 팝업 열기, 공통 코드 조회처럼 여러 화면에서 반복되는 로직을 gfn 접두어 전역 함수(gfnAlert, gfnOpenPopup, gfnGetCommonCode 등)로 한 번만 만들어 공용으로 쓴다. 화면마다 같은 로직을 새로 짤 필요가 없고 문구·검증 규칙도 일관되게 유지된다.

WebView 연동

화면 안에 웹페이지를 띄울 땐 구형 WebBrowser 대신 WebView(Chromium 기반)를 쓴다. callScript()로 넥사크로에서 HTML 함수를 실행시키고, HTML 쪽은 FireUserNotify()로 데이터를 보내면 넥사크로의 onusernotify 이벤트에서 e.userdata로 받는다.

WebBrowser vs WebView

넥사크로에서 화면 안에 웹 페이지를 띄우는 컴포넌트는 두 가지다. 요즘은 Internet Explorer 자체를 더 이상 지원하지 않는 추세라, 실무·실습에서는 WebBrowser보다 WebView를 쓴다.

WebBrowser

Internet Explorer 엔진 기반. IE 자체가 더 이상 지원되지 않아 요즘은 잘 쓰지 않는다.

WebView

Microsoft Edge(Chromium 기반) 엔진. 실무·실습에서 주로 쓰는 최신 컴포넌트.

url 속성과 gfnGetServerUrl()

WebView의 url 속성에 주소를 지정하면 그 페이지가 화면 안에 로드된다. 서버 주소를 문자열로 직접 적지 않고, gfnGetServerUrl() 공통 함수를 호출해 현재 실행 환경(localhost·서버 IP·실제 배포 주소 등)에 맞는 웹 루트 경로를 동적으로 가져온 뒤, 그 뒤에 필요한 하위 경로를 이어붙여 최종 URL을 완성한다. 이렇게 하면 개발/테스트/운영 환경이 바뀌어도 소스 코드를 수정하지 않고 주소를 맞출 수 있다.

실행 결과

지정한 url의 웹 페이지가 WebView 컴포넌트 안에 그대로 로드된다.

서버 통신 개요

Web Server는 정적 자원을, WAS는 DB 조회 같은 동적 처리를 담당한다. 자바 쪽 조회 결과(RS, ResultSet)는 넥사크로가 바로 못 읽으므로 Dataset(DS) 형태로 변환하는 중간 모듈을 거쳐야 화면에 바인딩할 수 있다. 서버 쪽 데이터는 보통 VO·Map·List 형태인데, 이걸 넥사크로 Dataset과 서로 변환해주는 역할을 UiAdapter가 맡는다 — 값뿐 아니라 행의 추가/수정/삭제 상태까지 함께 변환한다.

transaction()의 6개 인자

순서대로 ① 요청 식별 이름, ② 서버 서비스 경로(URL), ③ 서버로 보낼 Dataset, ④ 서버에서 받아올 Dataset 매핑("화면Dataset=서버Dataset"), ⑤ 낱개 변수 파라미터, ⑥ 완료 후 실행할 콜백 함수명이다. 조회 결과 건수 등은 이 콜백 함수 안에서 확인해야 한다.

this.transaction("svcCheckUserId", "SvcUrl::user/checkUserId.do", "", "", "userId=" + nexacro.wrapQuote(userId), "fn_callback")

⑤ 파라미터 문자열과 공백 문제

파라미터는 "key=값" 형태를 공백으로 이어붙여 전달하는데, 값 자체에 공백이 있으면(예: "홍 길동"처럼 띄어쓰기 있는 이름) 그 공백 지점에서 값이 잘려 "홍"까지만 전달되는 문제가 생긴다. 주의: nexacro.wrapQuote()로 값을 감싸야 공백이 있어도 안전하게 전달된다.

Before
"empName=" + sEmpName

After
"empName=" + nexacro.wrapQuote(sEmpName)

실제 조회 함수 예시 — deptCode는 그냥 붙이고, empName은 wrapQuote로 감싼 모습이다.

③ Dataset 전송 범위: :u vs :a

Dataset을 서버로 보낼 때 뒤에 붙이는 :u는 변경된(추가·수정·삭제) 데이터만, :a는 전체 데이터를 보낸다. 전송량을 줄이려면 :u를 주로 쓰며, 여러 Dataset을 동시에 보낼 땐 공백으로 나열한다(예: "in_emp=ds_emp in_aa=ds_dept"). 수정·삭제된 행은 바뀐 값뿐 아니라 수정 전 원래 값도 함께 보내지는데, 서버가 그 원래 값을 기준으로 WHERE절을 만들어야 정확히 그 행을 찾아 처리할 수 있기 때문이다.

② URL을 별칭으로 관리(TypeDefinition-Services)

서버 주소를 코드에 직접 쓰지 않고 "EduUrl" 같은 PrefixID로 등록해두면 "EduUrl::save_emp.jsp"처럼 짧게 쓸 수 있다. 환경(개발/운영)이 바뀌어도 이 등록 값 한 곳만 고치면 돼서 유지보수가 쉬워진다. TypeDefinition-Services에는 두 종류가 있다: 넥사크로가 기본 제공하는 Resource Service(theme, imagerc, font 등 리소스 경로)와, 개발자가 직접 추가하는 User Service(EduUrl, SvcUrl 같은 서버 API 별칭).

⑥ Sync/Async와 콜백의 중요성

넥사크로 기본 통신 방식은 비동기(Async)다. transaction() 호출 직후 다음 줄에서 바로 결과를 읽으면 아직 서버 응답이 도착하기 전이라, 방금 조회한 실제 값이 아니라 화면에 미리 넣어둔 샘플 값 등 엉뚱한 값을 보게 된다. 반드시 지정한 콜백 함수 안에서 결과를 처리해야 한다. 아래는 실제 콜백 함수 예시 — errCd가 음수면 실패로 보고 바로 알림 후 종료하고, 정상이면 svcId로 어떤 요청의 응답인지 구분해 분기 처리한다(빨간 박스 = 실패 처리 구간).

CORS와 NRE

3계층 구조와 MVC

서버는 Spring 기반 전자정부 프레임워크의 MVC 패턴을 따르며, 요청은 Controller → Service → Mapper → DB 순으로 내려가고 결과는 반대로 올라온다. 계층을 나누면 화면·로직·SQL이 서로 분리되어 유지보수가 쉬워진다.

Controller 작성 요소

@RequestMapping으로 요청 경로를 지정하고, 낱개 값은 @ParamVariable, Dataset 전체는 @ParamDataSet으로 받는다.

@RequestMapping(value="edu/getEmpList.do")
public NexacroResult getEmpList(
    @ParamVariable(name="deptCode") String deptCode) { ... }

NexacroResult로 응답 구성하기

Controller의 반환 타입은 NexacroResult다. 여기에 addDataSet()으로 목록 데이터를, addVariable()로 단일 값을 담아 반환하면 화면의 transaction 콜백에서 지정한 이름 그대로 받아볼 수 있다.

NexacroResult rst = new NexacroResult();
rst.addDataSet("outEmp", resultData);      // Dataset(목록) 응답
rst.addVariable("fvTotalCnt", totalCount); // 단일 값 응답
return rst;

실제 UserController 예시 — 파라미터 없이 조회해서 dsList란 이름의 Dataset으로 응답한다.

Service/Mapper 위임 구조

Controller는 직접 DB에 접근하지 않고 Service에 위임한다. Service는 인터페이스(예: NexaEduService)와 구현체(NexaEduServiceImpl)로 나뉘고, 구현체는 다시 Mapper 인터페이스(NexaEduMapper)를 호출한다. Mapper 인터페이스는 메서드 시그니처만 갖고 있고 실제 SQL은 짝을 이루는 Mapper.xml 파일에 있다. 아래는 회원 목록 조회(selectUserList) 하나가 Service 인터페이스 → ServiceImpl → Mapper 인터페이스 → Mapper.xml SQL까지 그대로 이름을 이어가며 내려가는 실제 예시다.

RowType 분기 처리

저장 시에는 Dataset의 각 행에 자동 기록된 RowType(추가/수정/삭제 상태)을 확인해 insert/update/delete 메서드를 각각 분기 호출한다. 여러 상태의 행이 한 번에 섞여 들어와도 이 분기로 한 번의 저장 요청에서 모두 처리된다.

switch (row.get("DataSetRowType")) {
  case DataSet.ROW_TYPE_INSERTED: mapper.insertEmp(row); break;
  case DataSet.ROW_TYPE_UPDATED:  mapper.updateEmp(row); break;
  case DataSet.ROW_TYPE_DELETED:  mapper.deleteEmp(row); break;
}

파일 업로드 서버 처리

서버 Controller는 MultipartHttpServletRequest로 업로드 요청을 받는다. 지정된 저장 폴더가 없으면 File.mkdirs()로 새로 만들고, 같은 이름의 파일이 이미 있으면 날짜·시간을 붙인 새 파일명을 만들어 덮어쓰기를 막는다. transferTo()로 실제 디스크에 저장한 뒤, 저장된 파일 정보(FILE_ID·FILE_NAME·FILE_SIZE)를 새 행으로 담은 Dataset을 응답으로 돌려준다.

FileUpTransfer 클라이언트 흐름

화면 쪽에서는 FileUpTransfer00.upload(...)를 호출해 업로드를 실행하고, 성공하면 발생하는 onsuccess 이벤트의 e.datasets[0]에서 서버가 돌려준 파일 정보를 꺼낸다. 이 콜백 안에서 바로 다음 단계(예: 회원가입 완료 처리 함수)를 이어서 호출하는 체이닝 패턴이 자주 쓰인다 — 업로드할 파일이 없으면 이 단계를 건너뛰고 바로 다음 처리로 넘어가면 된다.

페이징 데이터 조회 흐름

화면에서 cnt(한 페이지 개수)·offset(시작 위치)을 파라미터로 보내면 서버가 그 구간만 조회해서 돌려준다. 전체 흐름은 화면 transaction(cnt, offset) → Controller → Service → Mapper → SQL 실행 → 결과가 역순으로 반환 → Controller가 NexacroResult에 목록+총건수를 담아 응답 → 콜백이 그리드·페이지 버튼을 갱신 순서다. 예를 들어 페이지 크기 5, offset=20이면 21~25번째 행만 조회해온다. 페이지 번호가 바뀔 때마다 offset만 다시 계산해서 재요청한다.

아이디 중복 체크 처리 패턴

화면이 입력된 아이디를 보내면 서버는 COUNT 쿼리로 결과를 fvIdCnt에 담아 돌려준다. 개수가 0보다 크면 errorCode 100 + "이미 등록된 아이디입니다" 메시지를, 0이면 errorCode 200(사용 가능)을 반환하는 식으로 에러코드 자체를 결과 판별에 활용하는 패턴이다.

로그인과 전역 Dataset(gdsUser)

로그인 성공 시 서버가 돌려준 사용자 정보를 gdsUser 같은 애플리케이션 전역 Dataset에 채워두면, 이후 어느 화면에서든 다시 서버에 묻지 않고 바로 꺼내 쓸 수 있다.

this.transaction("svcLoginUser", "SvcUrl::user/LoginUser.do", "", "gdsUser=gdsUser", "userId=" + ... + " pass=" + ..., "fn_callback")

로그인/회원 정보를 담는 실제 tb_user 테이블 구조 — USER_ID가 PK이고 PASS·USER_NAME·EMAIL 등은 대부분 NULL 허용이다.

파라미터 형태별 처리

문자열 하나만 넘어올 땐 이름이 없으므로 _parameter 예약어로 받아야 한다. 조건이 여러 개면 VO 클래스(예: NexaEduVo)로 묶어 parameterType="com.edupack.edu.vo.NexaEduVo"로 지정하고 필드명 그대로(#{deptCode}, #{empName}) 쓴다. Dataset을 그대로 넘길 땐 parameterType="map"으로 받아 Dataset 컬럼명(COL_DEPT 등)을 그대로 조건식에 쓴다.

#{ } 바인딩과 조건절 자동 처리

#{파라미터명}은 값을 SQL 인젝션 없이 안전하게 채워 넣는 문법이다. <if> 태그로 조건절 자체를 생략 가능하게 만들 수 있고, <where> 태그를 쓰면 조건이 하나라도 참일 때만 WHERE를 붙이고 불필요한 첫 AND도 자동으로 지워준다. 조건이 두 개 이상일 때 VO + <where>/<if>를 함께 쓰는 예시:

<select id="getEmpListParam2" parameterType="com.edupack.edu.vo.NexaEduVo" resultType="map">
  SELECT * FROM tbl_employees
  <where>
    <if test="deptCode != null and deptCode != ''">AND DEPT_CODE = #{deptCode}</if>
    <if test="empName != null and empName != ''">AND EMP_NAME = #{empName}</if>
  </where>
</select>

Mapper.xml 조회 SQL

하나의 Mapper.xml 안에 여러 <select id="..."> 태그를 두고 조건 유무·형태별로 SQL을 나눠 작성한다. 화면 Dataset 컬럼명과 맞추기 위해 AS로 별칭을 붙이는 경우가 많다 — 공통 코드처럼 분류/세부값 구조인 테이블도 같은 방식으로 별칭을 맞춰 조회한다.

SELECT DET_CODE AS CODE, DET_NAME AS NAME FROM tbl_common_code WHERE MST_CODE = 'POSITION'

Insert/Update/Delete 매퍼

<insert>/<update>/<delete> 태그로 각각 정의하며, update·delete는 대개 PK 컬럼(예: EMP_ID)을 WHERE 조건으로 사용한다. 서버 Service 단계의 RowType 분기와 짝을 이뤄, 저장 버튼 한 번으로 여러 행의 추가/수정/삭제가 한꺼번에 처리된다.

UPDATE tbl_employees SET EMP_NAME = #{EMP_NAME}, ... WHERE EMP_ID = #{EMP_ID}
DELETE FROM tbl_employees WHERE EMP_ID = #{EMP_ID}

중복체크·로그인 인증 SQL

아이디 중복 체크는 COUNT(*)로 존재 개수만 확인한다(0=사용 가능, 1 이상=이미 존재). 로그인은 아이디+비밀번호로 COUNT를 세어 성공 여부만 판단하는 방식과, 조건에 맞는 회원 정보를 통째로 조회하는 방식을 함께 쓴다 — 회원가입 저장 시에는 now()로 가입일시를 DB 서버 시각 기준으로 자동 기록한다.

-- 중복 체크
SELECT COUNT(*) FROM tb_user WHERE USER_ID = #{userId}

-- 로그인 (존재 여부 + 데이터 조회를 함께 씀)
SELECT COUNT(*) FROM tb_user WHERE USER_ID = #{userId} AND PASS = #{pass}
SELECT USER_ID, USER_NAME, EMAIL, TEL_NO, PROFILE FROM tb_user
  WHERE USER_ID = #{userId} AND PASS = #{pass}

이 SQL을 화면 쪽에서 어떻게 부르고 결과를 어떻게 판별하는지는 실전 연동 패턴 항목의 "아이디 중복 체크"·"로그인과 전역 Dataset" 부분에 이어진다.

페이징 — ROW_NUMBER()와 LIMIT/OFFSET

ROW_NUMBER() OVER(ORDER BY ...)로 순번을 매기고, LIMIT/OFFSET으로 필요한 구간만 잘라온다. 화면에서 넘긴 cnt/offset 값을 그대로 #{cnt}/#{offset}에 바인딩하는 방식으로 페이지마다 다른 구간을 조회하며, 전체 건수는 별도의 COUNT 쿼리로 함께 가져와 페이지 버튼 개수를 계산하는 데 쓴다.

<select id="getPageData" parameterType="map" resultType="map">
  SELECT ROW_NUMBER() OVER(ORDER BY ID ASC) AS ROW_NUM, ID, NAME, DESCRIPTION, USE_YN, REG_USER
  FROM tbl_sample
  ORDER BY ID ASC
  LIMIT #{cnt} OFFSET #{offset}
</select>

<select id="getTotalCount" resultType="int">
  SELECT COUNT(*) AS totalcnt FROM tbl_sample
</select>

화면에서 cnt·offset을 어떻게 계산해 보내고 콜백에서 그리드·페이지 버튼을 어떻게 갱신하는지는 실전 연동 패턴 항목의 "페이징 데이터 조회 흐름"에서 다룬다.

공통 코드 테이블 설계

직급·부서·취미처럼 자주 안 바뀌는 코드들을 각각 테이블로 만들지 않고, MST_CODE(분류)·DET_CODE(세부값) 구조의 공통 코드 테이블(tbl_common_code) 하나로 모아 관리한다 — 예를 들어 MST_CODE=POSITION 그룹 안에 10=대표이사, 20=이사, 30=부장처럼 DET_CODE/DET_NAME 쌍이 나열되는 식이다. 앱 시작 시 한 번만 전역으로 조회해두면 불필요한 서버 통신을 줄일 수 있다.

HeidiSQL로 DB 직접 확인

HeidiSQL 같은 DB 툴로 실제 테이블 데이터와 구조를 미리 확인한 뒤 Mapper.xml의 SQL을 작성하면 컬럼명·데이터 형태를 헷갈리지 않고 정확하게 매핑할 수 있다.

세 가지 개발 방식

모바일 애플리케이션은 크게 Native App, Mobile Web, Hybrid App 세 가지 방식으로 만들 수 있다. 네이티브 앱은 속도가 빠른 대신 유지보수가 어렵고, 모바일 웹은 속도가 느린 대신 유지보수가 좋다. 이 둘의 장점을 모아 만든 것이 하이브리드 앱이라, 개발 생산성과 유지보수를 동시에 해결할 수 있다.

① Native App

OS가 제공하는 언어와 개발도구로 직접 만드는 방식이다. 안드로이드와 iOS가 언어·개발도구·패키지 형식·스토어까지 전부 다르기 때문에, 같은 앱이라도 양쪽을 따로 만들어야 한다.

② Mobile Web

웹 기술로 개발하고 모바일 브라우저에서 실행하는 방식이다. 데스크톱 웹 페이지를 모바일 해상도로 줄여놓은 것으로 볼 수 있다. 웹 표준을 쓰므로 표준화된 개발이라는 장점이 있지만, 네이티브 앱보다 속도가 느리고 카메라 같은 디바이스 연동 기능을 쓸 수 없다.

③ Hybrid App

모바일 웹과 네이티브 앱을 합친 형태다. 모바일 웹으로 먼저 개발한 뒤 크로스 프레임워크로 네이티브 앱으로 변환하는 방식이라, 처음부터 직접 만드는 게 아니라 이미 만들어진 것을 바꾸는 셈이다. 디바이스 연동과 앱 구동에 필요한 부분만 네이티브 언어를 쓰기 때문에 안드로이드 브라우저 파편화를 줄일 수 있고, OS별로 콘텐츠를 따로 만들 필요가 없어 개발·유지보수가 쉽다.

개발 방식 비교

구동속도·성능은 네이티브가, 제작 편의성·개발 가성비·업데이트 용이성은 모바일 웹이 앞선다. 하이브리드는 모든 항목에서 중간값을 가진다 — 속도가 정말 중요한 경우가 아니면 실무에서는 하이브리드를 많이 쓴다.

넥사크로는 어디에 속할까?

넥사크로는 모바일 웹과 하이브리드 앱 둘 다 가능하다. 모바일과 데스크톱의 개발 차이에서 가장 중요한 건 화면 크기로, 개발 방법 자체는 비슷하지만 UI가 가장 크게 달라진다. 모바일 웹으로 만들 경우 카메라·SNS 같은 디바이스 권한을 따로 열어주어야 한다.

모바일 퍼스트

웹 화면을 그대로 모바일로 옮기는 건 쉽지 않다. 그래서 모바일을 먼저 개발하는 "모바일 퍼스트"가 권장된다. 작은 화면에 우선 채울 것을 고민해 결정한 뒤, 화면이 커짐에 따라 채울 것을 전략적으로 설계하는 "채움의 미학"으로 접근한다.

반응형 웹 (Responsive)

CSS3 미디어쿼리를 이용해 스크린 크기에 따라 레이아웃 구성을 다르게 하는 방식. 하나의 소스·하나의 URL로 모든 기기에 대응하므로 제작·관리비가 저렴하고 검색 노출에도 유리하다. 다만 한 화면에 많은 콘텐츠를 넣는 문화에서는 구축이 복잡하고, 디바이스별 모든 페이지를 로드해 로딩이 길어질 수 있다.

넥사크로에서는 position 속성 설정으로 대응한다.

적응형 웹 (Adaptive)

정해진 몇 가지 화면 크기를 기준으로 두고 비율에 맞춰 페이지를 구성하는 방식. 해당 디바이스의 CSS·소스만 로드하므로 성능 이슈가 덜하고 그리드 형태 데이터의 가독성을 높일 수 있다. 다만 기기별로 페이지를 각각 제작해야 하고, 수정 사항이 생기면 나머지 페이지도 전부 고쳐야 해 유지보수가 불편하며 조금 부자연스러울 수 있다.

넥사크로에서는 MLM 기능으로 대응한다.

Nexacro N24는 position 속성과 MLM(Multi Layout Manager) 두 가지를 모두 제공하므로 반응형·적응형 둘 다 가능하다. 요즘은 반응형 웹이 많이 쓰인다.

실습 — 픽셀 단위 vs 퍼센트 단위

폼에 버튼을 올릴 때 크기·위치를 픽셀로 지정하면 창을 줄여도 리사이즈되지 않고(적응형 성격), 퍼센트로 지정하면 창 크기에 따라 같이 늘고 줄어든다(반응형 성격).

프로젝트 생성

데스크톱 프로젝트와 만드는 순서는 같고, 마법사에서 Screen을 Phone으로, Frame Template을 Full로 지정하는 점만 다르다. 그러면 화면 전체를 채우는 Form_Work 골격이 함께 생성된다.

테스트 — 에뮬레이터와 웹 브라우저

실행 대상에서 Nexacro Emulator를 고르면 모바일 테스트 전용 창이 뜬다. 화면을 자유롭게 바꿀 수 있어 세로 모드·가로 모드를 모두 확인할 수 있다.

웹 브라우저에서도 테스트할 수 있다. 크롬 개발자도구의 디바이스 목록에서 기종을 골라 실제 해상도로 확인하는 방식이다.

MLM (Multi Layout Manager) — 레이아웃 여러 개 만들기

Form 화면 상단의 [+] 버튼으로 레이아웃을 추가한다(예: 768 × 480). 레이아웃을 만들어두고 퀵뷰를 실행하면, 화면 사이즈를 조절할 때 그 크기에 맞는 레이아웃으로 자동 전환된다.

주의 — 추가된 레이아웃에서는 컴포넌트를 새로 선택·추가할 수 없다. 두 번째 레이아웃은 컴포넌트의 위치만 바꾸는 용도다.

Multi Screen — Application 추가

File > New > Application으로 Screen을 하나 더 추가하면(예: Desktop_screen) Environment > ScreenDefinition과 Application Information에 각각 등록된다. 컴포넌트의 screenid 속성으로 어느 스크린에서 보일지 지정할 수 있다.

X-PUSH는 업무 시스템이 수시로 만들어내는 정보/메시지를, 이를 필요로 하는 사용자들에게 발생 시점에 실시간으로 전송하는 Push Server다. 바로 이 "발생 시점에 받는다"는 것이 푸시의 핵심 기술이다. 데스크톱과 모바일 환경을 모두 지원하며, Nexacro N의 NRE(Windows·iOS·Android)와 WRE에서 쓸 수 있다.

왜 필요한가 — 폴링 방식의 문제

폴링(Polling)은 클라이언트가 일정한 주기를 가지고 서버에 계속 요청해서 메시지를 가져오는 방식이다. 주기가 짧으면 서버 성능에 부담이 가고, 길면 정보의 적시성이 떨어진다. 푸시는 이 딜레마 자체를 없앤다.

그 밖에 비동기 메시지 수신이 필요한 경우, 배치 결과나 인스턴스 메시지처럼 모든 메시지를 기다리며 대기하고 싶지 않은 경우, 그리고 클라이언트가 오프라인일 때도 반드시 전달되어야 할 메시지가 있는 경우에 쓴다.

X-PUSH의 특징

1

단독 실행 (stand-alone) — WAS 같은 다른 프로그램에 연결되지 않고 독립적으로 실행된다.

2

연결지향형 서버 — 패킷 전송 전에 발신·착신 간 논리적 통신 경로를 미리 설정한 뒤 데이터를 보낸다.

3

신뢰성 메시지 전송 — 사용자가 오프라인이라 못 받으면 저장해 두었다가 온라인이 되면 자동 전송한다. Recovery 기능으로 DB 오류 시 메시지 유실도 방지한다.

4

모바일 알림(Notification) — 앱이 꺼져 있어도 FCM·APNS와 연동해 알림을 띄운다.

5

서버 확장 및 분산 구성 — 사용자 수에 맞춰 서버를 늘릴 수 있다.

6

최고의 성능 보장 — 실시간·신뢰성 전송 방식 양쪽 모두에서.

기본 설정은 사용자 5,000명 기준이다. 접속 건수가 5,000을 넘어가면 X-PUSH 기기를 여러 대 설치해 분산한다.

세 단계로 끝나는 작동 방식

1

X-PUSH Client(사용자)가 수신을 원하는 TOPIC을 서버에 등록(Subscribe)하고 메시지 수신 상태로 대기한다.

2

외부(Back End System)의 Message Provider가 'TOPIC + 메시지'를 생성해 X-PUSH 서버에 공급(Provide)한다.

3

X-PUSH 서버가 등록된 TOPIC에 매칭되는 메시지를 해당 사용자에게 전달(Push)한다.

모든 역할은 서버가 한다. 즉 X-PUSH가 전달을 해서 사용자 화면이 받는 구조이며, 이것이 곧 실시간 메시지 주고받기다.

수신자에게 메시지를 전달하려면 공급자가 메시지 포맷을 먼저 정의해야 한다. 이때 쓰는 구조가 Topic으로, 메시지가 매칭되는 하나의 키 값을 가리킨다. 같은 Topic Key를 가진 수신자에게만 메시지가 전달된다.

Topic Type

메시지의 종류를 나타내는 일종의 그룹 키. 반드시 4byte(4자리)로 만들어야 한다 — 예: 0000, A001, NOTI

Topic Id

특정 타입의 메시지 중에서 다시 골라내기 위한 개별 키. 예를 들어 주식 알림이라면 Topic Type이 주식, Topic Id가 증권사 아이디가 되는 식이다.

메시지 사이즈 제약

Field Values는 실제로 전달하려는 내용이며, 하나의 메시지에 여러 개의 값을 만들 수 있다. 다만 구분자를 포함한 크기 제한이 있다.

① 실시간 메시지 — 지금 접속한 사람에게만

접속해서 토픽을 등록해 둔 클라이언트에게 바로 쏘는 방식이다. DB를 거치지 않으므로 빠르지만, 놓친 메시지는 재수신이 불가능하다.

② 신뢰성 메시지 — 못 받으면 다시 준다

메시지를 DB에 저장해두기 때문에 못 받은 건 재요청이 가능하다. 즉 테이블이 미리 만들어져 있어야 쓸 수 있다. Provider가 메시지를 보내면 서버가 T_TOPIC·T_USER_MESSAGE에 insert하고, 클라이언트가 받은 뒤 ackn(엔진 응답)과 responseMessage()(수신 확인)를 보내면 서버가 메시지 상태를 update한다.

사용자가 메시지를 보면 DB의 MESSAGE_STATE 값이 2가 되고, 안 보면 0으로 남는다. 모바일도 동작 방식은 비슷하다.

실습 — 수신 화면과 발송 화면

수신 화면에서는 프로젝트 아이디·프로토콜 버전과 접속 주소(tcp://localhost:50001, http://localhost:50000)를 확인한 뒤 xpush에 연결하고 토픽을 등록한다. 신뢰성 메시지를 쓸 때는 최초 한 번 사용자 등록을 해야 하며, 미수신 메시지 요청·개수 확인·디바이스 등록도 여기서 한다.

실시간 메시지 발송

신뢰성 메시지 발송

수신 콜백에서 두 방식을 구분하는 법

subscribe에 넘긴 콜백 함수로 메시지가 들어온다. 여섯 번째 인자 ActionType이 "PUSH"면 실시간, "RELI"면 신뢰성 메시지다. 신뢰성 메시지는 받은 것으로 끝이 아니라 sendResponse(MessageId)로 수신 확인을 되돌려줘야 서버가 "읽음"으로 처리한다.

this.fn_push_callback = function(Row, ChangeColumn, AllColumns, Type, ActionType, MessageId)
{
  this.taLog.set_value("ActionType : " + ActionType + "\n"
    + "Row : " + Row + "\n"
    + "MessageId : " + MessageId + "\n\n"
    + this.dsMessage.saveXML());

  if (ActionType == "PUSH")   // 실시간 메시지 — 받고 끝
  {
  }
  if (ActionType == "RELI")   // 신뢰성 메시지
  {
    this.XPush00.sendResponse(MessageId);  // 수신 확인 메시지 전송
  }
};

오프라인이었다면 — 미수신 메시지 재요청

신뢰성 메시지는 DB에 남아 있으므로, 다시 접속했을 때 requestMessage(topicType, topicId)로 못 받은 메시지를 끌어올 수 있다. 개수만 확인하는 requestMessageCount()도 있지만 실무에서 쓸 일은 거의 없다.

모바일 앱은 항상 켜져 있을 수 없다. 그래서 앱이 background 상태일 때는 구글(Android)의 FCM과 애플(iOS)의 APNS를 거쳐 알림을 띄운다. 알림은 신뢰성 메시지 전송에 의해 발송되며, 사용자가 알림을 눌러 앱을 활성화하면 X-PUSH와 다시 연결(Runtime 50001)해서 미수신 메시지를 요청한다.

디바이스 토큰 등록

알림을 받으려면 어느 기기로 보낼지 서버가 알아야 한다. connect() → registerTopic()(UserID·Topic 등록) → registerDevice()(디바이스 토큰 등록) 순으로 진행하며, 각각 T_TOPIC에 insert된다. 최초 한 번 사용자 등록을 하면 DB에 저장되는 구조다.

클라이언트 쪽 코드는 한 줄이다. 디바이스 토큰 자체는 system.notificationtoken에 들어 있어 로그로 확인할 수 있다.

// 모바일에서만 사용하는 기능
this.btn_RGST_onclick = function(obj:nexacro.Button, e:nexacro.ClickEventInfo)
{
  this.taLog.set_value("deviceID : [" + system.notificationtoken + "]");
  this.XPush00.registerDevice();
};

등록 결과는 onsuccess의 e.action == 6으로 돌아온다. 이미 등록된 기기를 다시 등록하면 -1072가 뜨는데 이건 정상 오류라 무시해도 된다.

클라이언트가 여러 곳(Window)에서 접속되어 있는 경우 모바일 메시지는 전송하지 않는다 — 웹이 기준이며 내부 정책이라 선택할 수 없다.

디바이스 토큰과 알림 이력은 각각 T_MOBILE, T_NOTIFICATION 테이블에서 확인한다. 모바일의 provider는 백엔드다.

FCM을 쓰려면 google.com 회원가입 후 FCM API 서버 KEY와 발급자 ID를 생성해야 한다.

메시지를 보내는 쪽은 Provider API를, 받는 쪽은 X-PUSH Object(Client Adaptor)를 쓴다. 백엔드가 Provider API로 메시지를 만들어 X-PUSH에 넣으면, 클라이언트 어댑터가 그것을 Message Layout(XML) 기준으로 파싱해 Dataset에 담아준다.

this.Form_onload = function(obj:nexacro.Form, e:nexacro.LoadEventInfo)
{
  // XPush Message 송/수신을 위한 Layout 세팅

      && (nexacro._Browser == "Runtime"))
  {

  else
  {

this.Button00.text = "hello"; 처럼 직접 대입하는 방식은 N24에서 쓰고, this.Button00.set_text("hello"); 처럼 setter를 부르는 방식은 N21부터 써 온 방식이다. X-PUSH 설정도 마찬가지로 set_projectid()·set_protocolversion()·set_iplist() 형태로 건드린다.

연결·구독 — 클라이언트 스크립트

set_iplist()는 IP:PORT만 쓸 수도 있고 tcp://·tcps://·http://·https:// 프로토콜을 붙일 수도 있으며, 콤마로 여러 서버를 나열할 수 있다. connect()의 비밀번호 인자는 의미가 없다 — 연결 성공·실패는 리턴값이 아니라 이벤트로 온다.

// 연결 / 해제
this.XPush00.set_iplist(this.IpPort.value);   // "tcp://172.10.12.24:10081, ..."
this.XPush00.connect(this.loginUserID.value, "...");  // 비번은 의미없음
this.XPush00.disconnect();  // 해당 페이지를 꺼도 연결은 끊어진다

// 구독 / 구독 해제 — 메시지는 비동기라 "append"로 계속 쌓는다
this.XPush00.subscribe(topic_type, topic_id, this, this.dsMessage, "append", "fn_push_callback");
this.XPush00.unsubscribe(topic_type, topic_id, this, this.dsMessage, "append", "fn_push_callback");

// 사용자 등록 — 실시간 메시지와 달리 DB에 저장된다
var ret = this.XPush00.registerTopic(topic_type, topic_id);
this.XPush00.unregisterTopic(topic_type, topic_id);

// 미수신 메시지 (신뢰성) 재요청 / 개수 조회
this.XPush00.requestMessage(topic_type, topic_id);
this.XPush00.requestMessageCount(topic_type, topic_id);

topic_id 자리에 "ALL"을 넣으면 해당 Topic Type 전체를 대상으로 한다. requestMessageCount()는 실무에서 쓸 일이 거의 없다.

이벤트 처리 — onsuccess / onerror의 e.action

모든 요청의 결과는 XPush00_onsuccess와 XPush00_onerror로 돌아온다. 어떤 요청의 결과인지는 e.action 값으로 구분한다.

e.action 대응 메소드 비고
0connect()접속 완료 — 보통 여기서 바로 subscribe를 건다
1disconnect()접속 해제
2subscribe()구독 등록 — 이어서 registerTopic을 호출
3unsubscribe()구독 해제
4requestMessage()미수신 메시지 요청
5sendResponse()신뢰성 메시지 수신 확인 전송
6 / 7registerDevice()
unregisterDevice()		모바일 디바이스 토큰 등록·해제
8 / 9registerUser()
unregisterUser()		유저 Topic 등록·해제
10requestMessageCount()e.message.returnvalue 배열에 topictype·topicid·count가 담긴다

이 구조를 이용하면 화면 로드 후 연결 → 구독 → 사용자 등록 → 미수신 메시지 수신까지 이벤트 체인으로 자동화할 수 있다.

this.XPush00_onsuccess = function(obj:nexacro.XPush, e:nexacro.XPushEventInfo)
{
  if (e.action == 0) {   // connect 성공 → 구독
    this.XPush00.subscribe("1000", "TOBEEDU01", this,
      nexacro.getApplication().gdsXPushMessage, "append", "fn_push_callback");
  }
  if (e.action == 2) {   // subscribe 성공 → 사용자 등록
    this.XPush00.registerTopic("1000", "TOBEEDU01");
  }
  if (e.action == 8) {   // registerUser 성공 → 못 받은 메시지 요청
    this.XPush00.requestMessage("1000", "TOBEEDU01");
  }
};

메시지 발송 화면 — Provider를 서버로 호출

넥사크로 화면에서 메시지를 보낼 때는 X-PUSH에 직접 꽂지 않는다. 선택한 TOPIC들을 dsProvider에 담아 서버의 Provider JSP를 transaction으로 호출하고, 실제 X-PUSH 공급은 서버가 Provider API로 처리한다.

this.btnSend_onclick = function(obj:nexacro.Button, e:nexacro.ClickEventInfo)
{
  if (!this.confirm("메시지를 전송하시겠습니까")) return;

  // 입력 검증
  if (this.dsTopic.getCaseCount("Chk == '1'") == 0) {
    this.alert("대상 TOPIC를 1개 이상 선택해주세요."); return;
  }
  if (this.edCode.value == "") { this.edCode.setFocus(); return; }
  if (this.taMSG.text  == "") { this.taMSG.setFocus(); return; }

  // 체크된 TOPIC만 골라 전송용 Dataset에 담는다
  this.dsProvider.clearData();
  for (var i = 0; i < this.dsTopic.getRowCount(); i++)
  {
    if (this.dsTopic.getColumn(i, "Chk") != "1") continue;

    this.dsProvider.addRow();
    var r = this.dsProvider.rowposition;
    this.dsProvider.setColumn(r, "PROJECT_ID", this.edit_setprojectid.value);
    this.dsProvider.setColumn(r, "PUSH_TYPE",  this.cmPushType.value);
    this.dsProvider.setColumn(r, "TOPIC_TYPE", this.cmTopicType.value);
    this.dsProvider.setColumn(r, "TOPIC_ID",   this.dsTopic.getColumn(i, "TOPIC_ID"));
    this.dsProvider.setColumn(r, "CODE",       this.edCode.value);
    this.dsProvider.setColumn(r, "MSG",        this.taMSG.text);
  }

  // 서버의 Service_XPush.jsp 호출
  this.transaction("SendMsg", "SvcURL::Service_XPush.jsp",
    "in_Provider=dsProvider:U", "",
    "argPUSH_TYPE=" + nexacro.wrapQuote(this.cmPushType.value)
      + " argPUSH_MSG=" + this.taMSG.text,
    "fn_callback");
};

this.fn_callback = function(svcid, ecd, emsg)
{
  if (ecd >= 0) this.alert("메시지를 정상적으로 발송하였습니다.");
  else          this.alert("메시지 전달실패 : " + emsg);
};

WRE와 NRE의 차이

WRE(Web Runtime Environment)는 이미 설치된 웹 브라우저에서 실행하므로 웹 서버에서 HTML·JS·CSS만 내려받아 바로 실행된다. 반면 NRE(Nexacro Runtime Environment)는 별도의 배포·설치 과정이 반드시 필요하다.

분류 설명 NRE WRE
엔진모듈스크립트·메모리·렌더링 처리, 런타임 엔진OX
배포파일프레임워크, 컴포넌트 라이브러리(자바스크립트)OX
개발소스Generate에서 변환된 코드(자바스크립트, CSS)OX

용어 정리

1

런처 서비스 — 윈도우 서비스로 동작하면서 지정한 넥사크로 엔진을 통해 앱을 실행한다. 단축 아이콘 생성이나 설치 리소스 배포도 처리할 수 있다.

2

넥사크로 엔진 — 윈도우에서 넥사크로 앱을 실행하기 위한 실행환경 파일. OS에 따라 32비트/64비트 모듈을 설치한다.

WRE 배포 = Packing 후 웹 서버에 Deploy

WRE 환경에서는 별도의 배포 작업이 필요 없고, 애플리케이션을 Packing해서 웹 서버에 올리기만 하면 된다. Deploy > Packing (Archive&Update)에서 왼쪽 Web Browser를 선택해 진행한다.

Packing 옵션 — Merge와 Compress

Packing 창 왼쪽 하단 또는 Options 창에서 Deploy 옵션을 설정한다.

Merge

넥사크로 자바스크립트 라이브러리 파일을 하나로 묶어 단순화한다. 미적용하면 index.html에 Framework.js·CompBase.js·Grid.js·ListView.js·Push.js 등 script 태그가 수십 개 나열되지만, 적용하면 통합된 파일 몇 개로 줄어 요청 수가 크게 감소한다.

Compress (코드 난독화)

공백·주석을 제거하고(Compress JS file), 변수명을 의미 없는 이름으로 바꾼다(Code Obfuscation). 단 eval이 들어 있는 함수는 난독화되지 않는다 — 이를 무시하고 강제 난독화하는 옵션도 있지만 권장되지 않는다.

원본과 소스는 분리된다 — Generate → Packing

넥사크로는 원본소스와 실행 소스가 분리돼 있다. 개발자가 만지는 것은 .xfdl 원본이고, Generate를 돌리면 웹이 읽을 수 있는 .xfdl.js가 만들어진다.

Generate Path는 프로젝트 설정에서 지정한다. Generate 경로와 Deploy 경로를 같은 경로나 하위 경로로 잡으면 프로젝트가 정상 동작하지 않을 수 있으니 반드시 분리한다.

그런데 Generate만으로는 부족하다 — 패킹이 하는 일

Generate된 js를 그대로 올리면 안 되고 Packing을 한 번 더 거쳐야 한다. 패킹하면 이름은 같은 js 파일이 다시 만들어지는데, 메모장으로 열어보면 내용이 다르다 — 공백을 걷어내고 난독화를 해서 HTML 소스코드가 그대로 보이지 않게 만든 것이다. 요청 수도 줄어들어 속도가 빨라진다. HTML 소스를 일일이 내려받을 필요가 없기 때문이다.

패킹 결과는 _web_ 폴더에 떨어진다. 사용자가 실제로 접속하는 곳이 바로 이 _web_이다.

패킹 결과 폴더 구조

Packing 완료 로그

넥사크로 라이브러리(nexacrolib) 안에도 여러 개의 js가 들어 있고, 이것들 역시 Merge·Compress 대상이다. WRE는 여기까지, 즉 패킹만 하면 끝난다.

CacheLevel — 파일을 언제 다시 받게 할 것인가

서비스마다 캐시 정책을 정할 수 있다. TypeDefinition > Services의 CacheLevel 컬럼에서 지정한다.

종류 설명
None캐시를 쓰지 않고 매번 서버에서 받는다. 주로 Dataset 관련 통신에 쓴다.
Dynamic
[기본값]		서버 파일이 갱신됐을 때만 받고, 아니면 로컬 캐시를 재사용한다. 초기·불안정한 단계에서 쓴다.
Session엔진을 기동할 때 한 번만 받고, 엔진이 종료될 때까지 로컬 캐시만 쓴다. 운영에서 안정권에 들어섰을 때 쓰는 값.
Static한 번 받은 파일은 엔진을 재실행해도 로컬 캐시만 쓴다(TypeDefinition의 서비스 그룹 버전이 바뀌면 다시 받음). NRE에서만 동작하고 WAR로는 안 되며, 국내는 네트워크가 좋아 잘 쓰지 않는다.

CheckVersion — 캐시를 새로 받게 만드는 스위치

Environment의 checkversion은 요청 URL 뒤에 쿼리 스트링(버전 숫자)을 붙일지 말지를 정한다.

false — 숫자가 안 붙는다

한 번 캐시로 받으면 그 뒤로는 더 받지 않는다. 갱신하려면 F12로 캐시를 직접 지워야 한다.

true — 뒤에 숫자가 붙는다

숫자가 바뀌면 캐시를 새로 받는다. 즉 유저 서비스를 고쳤을 때 버전만 올려주면 배포가 반영된다.

WRE 운영 환경에서 버전을 지정하는 위치는 세 군데다.

배포는 파일 단위가 아니라 폴더(서비스) 단위로 진행된다는 점을 함께 기억해 둘 것.

NRE는 사용자 PC에 실행 환경을 설치해야 하므로 WRE보다 챙길 것이 많다. 엔진 모듈, 배포 파일, 개발 소스가 모두 사용자 PC로 내려간다. 다르게 말하면 배포라는 작업 자체가 NRE 실행환경일 때 하는 일이다.

배포 순서 — 사용자가 직접 설치하게 만든다

다운로드 링크 → 배포 사이트 접속 → 런처와 엔진 설치 → 설치가 끝나면 웹 브라우저가 아니라 넥사크로 전용 브라우저가 뜨는 흐름이다. 설치는 사용자가 선택하도록 만들어야 하고 바로 설치되게 할 수는 없다.

실제 배포 사이트는 전용브라우저와 html5 중 무엇으로 실행할지 고르게 해 주고, 필요한 프로그램이 깔려 있는지 확인한다.

Build App — 설치 파일 만들기

사용자 PC에 내려갈 것은 ① 클라이언트 파일과 ② 넥사크로 엔진·런처다. 수동설치 파일도 함께 준비해 둔다. 배포용 exe 파일에는 디지털 서명을 반드시 포함해야 한다.

기본 넥사크로 엔진은 변경 없이 그대로 쓰지만, 설치 리소스나 앱 설치 파일을 쓰는 경우에는 Engine Setup Key와 설치 경로를 따로 지정할 수 있다.

Launcher

Launcher 서비스는 윈도우 서비스에 등록되어 동작하므로 등록 시 관리자 권한이 필요하다. 웹 브라우저가 Launcher와 통신할 때 데이터는 JSON 형식으로 주고받으며, Launcher에서 쓰는 변수는 대소문자를 구분하므로 주의한다.

고객 대응

NRE는 사용자 PC에 프로그램을 설치하는 방식이라, PC 환경과 권한 설정에 따라 설치 오류가 발생할 수 있다. 대응 CASE를 미리 작성해 사용자가 스스로 처리할 수 있도록 수동설치 파일과 안내 페이지를 준비해 두고, 1차 대응으로 해결되지 않으면 투비소프트 고객지원센터를 통해 지원받는다.

그래서 NRE와 WRE 중 무엇을 쓰나

로컬 DB를 쓰는 기능이나 데이터를 대용량으로 가져오는 경우에는 NRE를 쓴다. 그 외에는 실무에서 WRE를 훨씬 더 많이 쓴다.

운영 단계 주의사항

배포가 끝났다고 끝이 아니다. 오픈 시점에 오류가 가장 많이 터진다. 아래는 운영에 들어가기 전에 알고 있어야 할 것들이다.

1

제너레이트는 되돌릴 수 없다 — 넥사크로도 자바처럼 제너레이트된 소스만 있으면 원본 소스 없이 돌아간다. 다만 한 번 제너레이트된 소스를 원본으로 되돌릴 수는 없으므로, 수정은 반드시 원본을 고치고 다시 제너레이트하는 순서로 한다.

2

SPA라서 앞으로/뒤로 가기가 안 된다 — 넥사크로는 Single Page Application이고 엔진이 화면 전환에 관여하기 때문에 브라우저의 History가 동작하지 않는다. 일반 사용자에게는 불편할 수 있으므로, 화면이 바뀔 때마다 URL 주소를 함께 바꿔주면 앞으로/뒤로 가기를 쓸 수 있다.

3

개인화 저장 위치 — 로컬 스토리지에 저장하면 브라우저가 바뀌었을 때 공유되지 않는다. 기기·브라우저를 넘나들어야 하는 설정이라면 서버 DB에 저장해야 한다.

4

서버 타임아웃 — 일정 시간이 지나면 서버가 기록을 지운다. 인터넷뱅킹 로그인 시간이 만료되는 것과 같은 동작이라, 화면에서도 만료를 전제로 처리해야 한다.

5

막히면 넥사크로 화면에서 F1을 누르면 도움말이 열린다.

보안 — eval은 절대 쓰지 않는다

eval은 보안 코드 점검에서 바로 걸리는 메소드다. 게다가 eval이 들어 있는 함수는 패킹 시 난독화도 되지 않는다. 문자열로 객체나 함수를 찾아야 한다면 아래 방법을 쓴다.

// 오브젝트화 — 이름(문자열)으로 객체 찾기
var objGrid = this.all[sObjectId];         // 전부
var objGrid = this.components[sObjectId];  // 화면에 보이는 것 (visible)
var objDs   = this.objects[sObjectId];     // 안 보이는 것 (invisible, Dataset 등)

// 이름으로 함수 호출
this[fn_ID].call(null, 1, 2);
this.lookup(fn_ID).apply(null, [1, 2]);

// 절대 eval을 쓰면 안 된다!

통신 구간 암호화

넥사크로의 데이터 통신 방식은 네 가지가 있는데 기본적으로 암호화되어 있지 않다. 통신 암호화 기능은 별도 제품을 구입해야 쓸 수 있다.

간단하게는 http를 https로 바꾸면 보안 프로토콜로 전환된다. 다만 서버가 암호화하는 시간이 더 들어 속도는 느려지고, https라고 해서 완전히 막아주는 것도 아니다.

투비소프트와 넥사크로

투비소프트는 기업용 업무 화면(UI) 솔루션을 만드는 회사이고, 넥사크로는 그 화면을 만드는 개발 도구다. IDE인 NEXACRO Studio로 화면을 만들면 .xfdl 파일이 생성된다.

프로젝트 생성 절차

New로 새 프로젝트를 만들 때 이름/경로, 대상 디바이스, 초기 화면 구성을 순서대로 지정한다. 생성되는 프로젝트에는 Environment, TypeDefinition(Objects·Services), Application Information 같은 설정 항목이 기본으로 함께 만들어진다.

Project Explorer vs Resource Explorer

Project Explorer는 환경설정·컴포넌트 정보·서비스 경로 같은 프로젝트 구조를 담고, Resource Explorer는 Theme 등 디자인 리소스를 담는다. Form에 컴포넌트를 추가하면 관련 디자인 요소가 자동으로 Resource Explorer에 반영된다.

외부 Theme 폴더 가져오기

Resource Explorer에서 "Open Theme Folder"로 실제 저장 경로를 연 뒤 폴더를 복사해 넣는다. 주의: 외부에서 직접 복사한 파일은 자동 인식되지 않으므로 반드시 Refresh를 해줘야 프로젝트에 반영된다.

외부 화면 폴더 가져오기

CompGuide 같은 외부 폼 폴더는 단순히 복사만 해서는 인식되지 않는다. TypeDefinition의 Services에 이름·경로·타입(form)을 등록해야 그 폴더의 화면을 실제로 쓸 수 있다.

Nexacro N Reference Guide

Help 메뉴의 이 도움말에서 컴포넌트별 속성·메소드·이벤트뿐 아니라 내부 구조(Control Map)까지 확인할 수 있어, 세부 스타일을 지정하기 전에 어떤 하위 요소가 있는지 미리 파악하기 좋다.

mainframe 크기 설정

Application Information의 mainframe 속성에서 전체 창의 width/height, 정렬 방식을 설정한다. 이 값은 Modaless 팝업을 화면 정중앙에 계산해 띄울 때 기준으로 쓰인다.

.xjs/.xfdl과 Generate

.xjs 파일은 실제로는 XML 안에 스크립트를 담은 형식이다. 브라우저에서 실행하려면 Generate 과정을 거쳐 xfdl/xjs를 실제 js 파일로 변환해야 한다.

Local Web Server의 한계

스튜디오 내장 Local Web Server는 실제 백엔드에 연결되어 있지 않아 화면·레이아웃 확인용으로만 적합하다. 서버 데이터 연동까지 확인하려면 실제 Web Server(Tomcat 등)로 실행해야 한다.

webapp 폴더와 Generate Path

Java 웹 프로젝트의 src/main/webapp이 실제 웹 주소의 루트가 된다. Generate Path를 이 webapp 하위 경로로 맞춰두면 변환된 결과물이 곧바로 서버가 읽을 수 있는 위치에 생성된다.

QuickView로 실서버 테스트

Run Environment를 Web Server로 바꾸고 실제 톰캣 주소를 지정하면, Generate된 결과물이 진짜 서버를 통해 로드되어 데이터 조회·수정까지 정상 테스트할 수 있다.

Application 추가와 Frame Template

Application Information에서 새 Application을 추가할 때 Frame Template을 "Full"로 두면 화면 전체를 채우는 기본 골격(Form_Work.xfdl)이 자동 생성되어, 매번 빈 화면부터 짤 필요가 없다.

전역 Dataset과 화면 계층 설계

로그인 정보처럼 앱 전체가 공유할 데이터는 전역 Dataset(gdsUser 등)에 두고, 하나의 뼈대 화면 안에서 상황에 따라 필요한 하위 화면(로그인/회원가입 등)만 바꿔 끼우는 구조로 설계하면 화면 간 연결을 이해하기 쉬워진다.

MDI 프레임 구조 요약

frameTop(상단 메뉴)·frameLeft(좌측 메뉴)·frameMdi(탭 관리)·frameWork(업무 화면 공통 틀)이 서로 맞물려 하나의 MDI 애플리케이션 골격을 이룬다. 각 프레임의 자세한 구현은 "넥사크로 소개" 쪽 Frame 구조 항목을 함께 참고하면 좋다.
